# Вопросы организаторам, допущения и источники

## 1. Уточнить в первую очередь

| Вопрос | Как ответ изменит решение |
|---|---|
| Какие сообщения/файлы, единицы, частоты и timestamp у ручки и одометрии? | Определяет адаптер и обработку времени |
| Одометрия дана по колесам/осям отдельно или одним агрегатом? | Определяет возможности диагностики отдельных отказов |
| Есть ли направление вращения, радиусы колес и аппаратные validity-флаги? | Определяет перевод единиц, реверс и проверки |
| Что означают положения ручки: тяга, выбег, разные тормоза, реверс? | Определяет форму нелинейной модели |
| Есть ли независимый эталон и можно ли использовать его для офлайн-обучения? | Определяет, какую точность можно проверить и как обучать модель |
| Разрешены ли начальные скорость/позиция и их доверие? | Определяет инициализацию и абсолютную/относительную координату |
| «Положение» — расстояние вдоль пути или координаты на карте? Есть ли маршрут и выбор ветви? | Определяет необходимость маршрутного преобразования |
| Как долго нужно переживать отказ и какие ошибки допустимы? | Определяет горизонты прогноза и переход в `INVALID` |
| Какой target CPU/ОС, частота, предельная задержка? Нужна ли hard real-time гарантия? | Определяет допустимость Python и объем C++-работ |
| Как оцениваются пропуски, `INVALID` и ковариация? | Определяет формат безопасного выхода и честное сравнение |
| Длительность хакатона и обязательные артефакты сдачи? | Определяет объем MVP и упаковку |

Запросить также описание трамвая, доступные характеристики тяги/торможения, диапазон загрузки, способ формирования проскальзывания в тестах и правила использования внешних библиотек. Не предполагать, что эти сведения будут доступны онлайн.

## 2. Что принято до ответов

| Допущение | Принято в документах |
|---|---|
| Команда | Пять человек, включая двух .NET/Vue full-stack |
| Время | 48 часов, отдельный сокращенный вариант на 24 часа |
| Режим движения | Вперед, продольная относительная координата |
| Runtime-вход | Только ручка, колеса, время и разрешенная конфигурация |
| Состояние старта | По разрешенной привязке либо условный `s0=0` и достоверные колеса для `v0` |
| Навигационная карта | Расширение при наличии разрешенной карты и маршрутной привязки |
| Среда | Humble на Ubuntu 22.04; Python-проверка бюджета задержек |
| Выход | Скорость, путь, ковариация и качество; совместимая ROS-одометрия |

## 3. Технические источники

Проверены 15 сентября 2026 года. Источники ниже подтверждают свойства платформы и сообщений. Предлагаемые формулы, разбиение команды, пороги и целевые метрики являются проектными решениями, которые еще предстоит проверить.

- [ROS 2 Humble: Features](https://docs.ros.org/en/humble/The-ROS2-Project/Features.html) — целевые платформы и клиентские библиотеки C++/Python.
- [ROS 2 Humble: Quality of Service](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Quality-of-Service-Settings.html) — reliability, history и совместимость издателей/подписчиков. Поиск вернул содержание страницы, прямое открытие при подготовке было ограничено защитой сайта; параметры необходимо сверить при настройке окружения.
- [Odometry.msg из ros2/common_interfaces, Humble](https://raw.githubusercontent.com/ros2/common_interfaces/humble/nav_msgs/msg/Odometry.msg) — точное определение полей и систем координат.
- [ROS 2 Design: Introduction to Real-time Systems](https://design.ros2.org/articles/realtime_background.html) — различие низкой задержки и гарантированного дедлайна, влияние ОС, памяти и блокирующих операций. Это архитектурный материал, а не сертификат real-time для конкретной сборки Humble.

## 4. Риски, влияющие на объем разработки

| Риск | Ранний признак | Действие |
|---|---|---|
| Нет независимого эталона | Для проверки выдана только та же колесная скорость | Разделить синтетические результаты и непроверенную реальную точность |
| Динамика ручки сложнее ожиданий | Одна ручка дает существенно разные реакции | Добавить задержку/режимы, ограничить область применения модели |
| Все колеса ошибаются одинаково | Межканальное согласие сохраняется при большой ошибке | Проверить предел наблюдаемости, консервативное качество и горизонт |
| Модель обучается на отказе | После буксования ухудшается чистый участок | Заморозить адаптацию, ввести гистерезис, вернуться к последним допустимым параметрам |
| ROS собирается только у одного человека | Нет повторного чистого запуска | Поднять общую Linux-среду и smoke-тест в первые часы |
| Жесткий дедлайн обязателен | Критерии требуют гарантии, а не p99 | Раннее решение о C++ и сокращение объема стенда |
| Веб-стенд задерживает интеграцию | Модель готова, сквозного запуска нет | Проверять ROS через CLI и записанные отчеты, подключать UI по контракту |

Первое командное обсуждение должно завершиться тремя результатами: согласованным смыслом входов, владельцами пяти потоков и зафиксированным контрактом v0.1. После этого каждый участник может сразу писать свой компонент.
