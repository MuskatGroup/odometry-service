## 1. Что сделано

### 1.1. Геометрия (B1, B2) — пакет `python/odometry_geometry`

Только стандартная библиотека Python 3.10, без ROS, numpy и pyproj. Публичный API совпадает с
разделом 5 плана.

- **Pathgraph.** Загрузка двух JSON, стабильные ASCII-имена маршрутов
  (`tallinskaya_to_shchukinskaya`, `shchukinskaya_to_tallinskaya`), длина каждого около 4709 м.
  `pose_at`, `body_pose_at`, `project` со статусами `MATCHED`, `AMBIGUOUS`, `OUT_OF_GRAPH`.
  За границей карты точка не прижимается к концу маршрута.
- **WGS84 в MGRS 37UCB.** Непрерывные метры без деления по модулю. Контрольная точка
  организаторов (55.8088325462547, 37.4602768500852) даёт x = 103501.6309, y = 85876.1201.
- **Антенны.** Положение и курс по двум антеннам (база 12,436 м), запасной вариант по одной
  антенне при известном курсе.
- **Ресурсы.** Около 7 МБ памяти, загрузка 0,25 с, пара `pose_at` + `project` около 74 мкс.
  Лимиты контейнера (0,5 ГБ, 2 ядра, 100 мс) выдерживаются с большим запасом.
- Тесты: `tests/test_geometry.py` (28 штук). Проверено, что `project(pose_at(s))` возвращает
  `s` с ошибкой меньше 5 см, а соседние пути различаются по направлению.

### 1.2. Эталон по GNSS и разбиение записей (B3)

- `dataset/analysis/gnss_reference.py`, класс `SpeedReferenceBuilder`: две GNSS-скорости
  сводятся в одну, положение `base_link` считается по двум антеннам и проецируется на
  Pathgraph, скорость сверяется с производной положения. Колёса как эталон не используются.
- `dataset/analysis/tram_bag.py`: чтение rosbag без ROS (sqlite + CDR), включая `NavSatFix`.
- `dataset/analysis/build_reference_table.py`: таблица эталона по каждой записи и разбиение
  на identification / validation / test **целыми записями**. Дубликаты (25 групп) всегда в одной
  части.
- Из 122 записей пригодны 75: 35 без GNSS-положения, 8 короче 2 минут, 4 почти целиком в депо.
- Проверка эталона: колёса (км/ч / 3,6) против эталона расходятся в среднем на 0,12 м/с.

### 1.3. Идентификация модели (B3)

- `dataset/analysis/identify_model.py`: таблицы тяги и торможения (7 позиций ручки × 7 скоростей),
  `tau`, сопротивление. Метод: неотрицательные наименьшие квадраты с монотонностью по
  позиции ручки и сглаженностью по скорости.
- Результат: `configs/models/default.yaml`, `30618.yaml`, `30639.yaml` (формат из раздела 5.1
  плана, плюс метрики validation и test).
- Скорость при работе **только по модели** на 10 секунд вперёд, тест: 0,667 м/с ошибки
  против 2,317 м/с у «держать скорость» (в 3,5 раза лучше).

### 1.4. Failure Lab на реальных записях (B4)

- `python/odometry_lab/src/odometry_lab/realdata.py`: реальная запись становится кейсом
  (км/ч в м/с, позиция ручки / 15), в реальный поток колёс вносятся отказы (заморозка,
  пропажа, всплески, проскальзывание, блокировка; одно и два колеса), результат сравнивается с
  эталоном.
- Команды: `real-benchmark` (пресеты × отказы × записи), `calibrate-noise` (подбор шумов),
  `real-run` (один запуск для сайта).
- Режимы GNSS `never`, `initial`, `intermittent-30/60/120` описаны функцией
  `gnss_availability`, но запускать их нечем (см. раздел 2, пункт 4).
- Подбор шумов EKF: `python/odometry_lab/src/odometry_lab/calibrate.py`.

### 1.5. Витрина и документы (B5)

## 2. Главные находки, которые нужно передать разработчику 1

1. **Стандартные шумы фильтра ломают его на реальных данных.** Он ложно отбраковывает
   исправные колёса, и на чистых данных ошибка 0,36–0,46 м/с против 0,05 у простого baseline.
   Я подобрал шумы по данным: `q_v` = 0,05, `q_a` = 3,0. После этого на тесте ошибка 0,070 м/с
   (baseline 0,075), а при отказе одного колеса 0,07–0,21 против 0,56–1,70. Значения лежат в
   `configs/models/*.yaml`.
2. **Отказ обоих колёс сразу остаётся слабым местом** (ошибка около 1,5 м/с, как у baseline при
   заморозке).
3. **Модель по одной ручке (B1) в ядре пока не работает**, потому что ядро не умеет читать мои
   таблицы (нужен загрузчик YAML).
4. **GNSS-коррекций в ядре нет**, поэтому режимы `initial` и `intermittent` и пресет «EKF + GNSS»
   не запускались. Метрики по ним стоят `null`, а не нулём.

Подробные таблицы: [VALIDATION.md](delivery/VALIDATION.md), раздел 4.

## 4. Открытые вопросы

### 4.1. Разработчику 1

1. Разрешены ли в `metrics` model YAML произвольные ключи? Я добавил туда
   `noise_calibration`, `test_velocity_rmse_mps` и другие; если загрузчик отвергает
   неизвестные поля везде, он упадёт на моих файлах.
2. Как ядро должно вести себя при `u` между 0 и первым узлом таблицы (0,067)? Сейчас я
   считаю, что при `u = 0` ускорение 0, а при `0 < |u| < 0,067` берётся значение первого узла
   (граница таблицы). Подходит?
3. Когда будет готов приём GNSS-коррекций? Без него блок «EKF + GNSS» плана остаётся
   `unavailable`.
4. Исправлена ли потеря колёсных сообщений на границе таймстампов (`OUT_OF_ORDER` при
   отставании `header.stamp`)? На реальных записях это отставание 35–70 мс.

### 4.2. Организаторам

1. **Формула оценки скорости.** Что судья считает «истинной» скоростью: одну из GNSS-скоростей,
   их среднее или что-то другое? Мой эталон строится по согласию двух приёмников.
2. **GNSS в закрытых тестах.** Из 122 выданных записей у 35 нет GNSS-положения вообще.
   Будет ли GNSS в закрытых тестах, и гарантирован ли он в начале?
3. **Запись вне Pathgraph.** Часть записей (например `30618_af7496f0`) целиком проходит в
   депо, в сотнях метров от карты. Бывают ли такие в закрытых тестах и что ожидается в
   `/result/position`?
4. **Запись `30639_e4379d7f`.** У неё нет валидного GNSS-положения. Это намеренно?
5. **Высотная система `z`.** Считается ли `z` от эллипсоида или геоида? Для проверки положения
   по XYZ это нужно знать.
6. **Масса и загрузка.** Меняются ли они между поездками одного трамвая? Профиль тяги от этого
   зависит, а масса в данных не наблюдается.
