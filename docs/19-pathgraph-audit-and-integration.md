## 1. Что выдали организаторы

В каталоге `dataset/Pathgraph` находятся два направленных маршрута:

| Файл | Направление | Точек | Длина XY | Длина XYZ |
|---|---|---:|---:|---:|
| `таллинская - щукинская.json` | Таллинская → Щукинская | 4 709 | 4 707,960 м | 4 708,562 м |
| `щукинская - таллинская.json` | Щукинская → Таллинская | 4 710 | 4 708,338 м | 4 708,927 м |

Оба файла имеют структуру:

```json
{
  "points": [
    {"x": 0.0, "y": 0.0, "z": 0.0, "tang": 0.0, "curv": 0.0}
  ],
  "paths": [
    {"ext_id": null, "point_indices": [0, 1, 2]}
  ]
}
```

Фактически `point_indices` последовательно перечисляет все точки файла. Медианный шаг
между точками близок к 1 м.

## 2. Семантика полей

Проверка геометрических производных даёт следующую трактовку:

| Поле | Семантика | Единица | Как проверено |
|---|---|---|---|
| `x`, `y` | локальная декартова позиция | м | расстояние между соседними точками ≈ 1 м |
| `z` | высота траектории | м | плавный профиль высоты |
| `tang` | угол касательной от оси `x` | рад | совпадает с `atan2(dy, dx)` |
| `curv` | знаковая кривизна | 1/м | совпадает с `d(tang)/ds` |

Медианная абсолютная ошибка `tang` относительно геометрической касательной около
`0,0004 rad`, 95-й перцентиль около `0,004 rad`. Медианная ошибка кривизны около
`6e-5 1/м`, 95-й перцентиль около `5e-4 1/м`.

Первый `tang` обратного маршрута больше `pi`, но эквивалентен правильному углу по
модулю `2*pi`. Поэтому любой загрузчик обязан нормализовать угол:

```python
yaw = atan2(sin(tang), cos(tang))
```

Два JSON — не один центральный путь, записанный в противоположных направлениях. Это
соседние рельсовые пути. При сопоставлении по обратной накопленной длине медианное
расстояние между ними около 3,74 м, 95-й перцентиль около 6,74 м. Выбирать файл нужно
по направлению движения, а не только по ближайшей точке.

## 3. Предполагаемая система координат

Координаты Pathgraph имеют диапазоны примерно:

```text
x: 99 156 ... 103 347 м
y: 84 861 ... 85 637 м
z: 144,8 ... 173,6 м
```

Экспериментальное преобразование GNSS, которое совмещает точки bag с графом:

```text
WGS84 → UTM zone 37N (EPSG:32637)
x_path ≈ easting  - 300000
y_path ≈ northing - 6100000
```

Это совместимо с идеей локальных координат внутри 100-км MGRS-ячейки, но пока остаётся
проверенной рабочей гипотезой, а не официальным контрактом. У организаторов нужно
подтвердить:

- точный `mgrs_grid`;
- horizontal и vertical datum;
- допустимую библиотеку/формулу преобразования;
- ожидаемый `frame_id`;
- относится ли `z` Pathgraph и GNSS altitude к одной высотной системе.

Смещения `300000/6100000` должны быть параметрами проекции, а не неименованными
константами в алгоритме.

## 4. Сопоставление с rosbag

Проверка выборок GNSS длинных записей показывает хорошее совмещение на основном
маршруте:

| Bag | Медианное расстояние до графа | Доля точек ближе 10 м |
|---|---:|---:|
| `30618_01f73500` | 0,298 м | 80,0% |
| `30618_2366c74a` | 0,471 м | 86,4% |
| `30639_0be558e2` | 0,383 м | 67,7% |

95-й перцентиль в этих записях достигает сотен метров. Это не похоже на небольшую
ошибку проекции: часть движения проходит вне двух выданных путей, вероятно по депо или
подъездным путям. Короткий bag `30618_0d865417` целиком находится примерно в 675 м от
графа и не подходит для проверки проекции на этот маршрут.

Следствия:

1. map matcher должен возвращать не только проекцию, но и расстояние до неё;
2. требуется настраиваемый порог принятия сопоставления;
3. состояние `OUT_OF_GRAPH` является штатным, а не исключением;
4. нельзя зажимать `s` в `[0, route_length]` и публиковать крайнюю точку как валидную;
5. метрики по Pathgraph надо считать только на участках с валидным match, отдельно
   публикуя coverage.

## 5. Контракт программного модуля

Рекомендуемый независимый от ROS API:

```python
class PathGraph:
    route_id: str
    length_m: float

    def pose_at(self, s_m: float) -> TrackPose: ...
    def project(self, x_m: float, y_m: float, yaw_rad: float | None) -> TrackMatch: ...
```

```python
@dataclass(frozen=True)
class TrackPose:
    x_m: float
    y_m: float
    z_m: float
    yaw_rad: float
    curvature_inv_m: float
    grade: float

@dataclass(frozen=True)
class TrackMatch:
    route_id: str | None
    s_m: float | None
    cross_track_m: float | None
    heading_error_rad: float | None
    status: Literal["MATCHED", "AMBIGUOUS", "OUT_OF_GRAPH"]
```

Загрузчик должен:

1. проверить top-level `points` и `paths`;
2. проверить конечность всех чисел и границы индексов;
3. собрать путь в порядке `point_indices`;
4. отклонить повторные/нулевые сегменты либо явно их диагностировать;
5. вычислить накопленную дуговую координату `s` по XYZ или по согласованному XY;
6. нормализовать `tang`;
7. построить сглаженный профиль `grade = dz/ds`;
8. подготовить пространственный индекс сегментов для быстрого поиска;
9. использовать стабильные ASCII `route_id`, не зависящие от имени файла.

Предлагаемые идентификаторы:

```text
tallinskaya_to_shchukinskaya
shchukinskaya_to_tallinskaya
```

## 6. Инициализация и runtime

### При наличии GNSS в начале

1. Преобразовать валидный GNSS fix в систему Pathgraph.
2. Найти несколько ближайших сегментов обоих маршрутов.
3. Спроецировать точку на каждый сегмент, а не на вершину.
4. Проверить cross-track distance и, когда движение уже началось, направление GNSS
   velocity относительно `tang`.
5. Выбрать `(route_id, s0)` только при достаточном отрыве лучшего кандидата.
6. После bootstrap отключить GNSS от рабочего оценивателя.

### Без GNSS

Стенд должен передать `route_id` и `initial_s`/initial pose через ROS parameters или
конфигурационный YAML. Угадывать абсолютную позицию только по контроллеру и скоростям
колёс невозможно. Если передан initial pose, его сначала следует проецировать на граф
с теми же проверками качества.

### Во время работы

Оцениватель хранит продольное смещение относительно старта:

```text
s_route(t) = s0 + delta_s(t)
```

По `s_route` линейно интерполируются `x/y/z`, а угол интерполируется через единичные
векторы или после корректного unwrap. Выход за диапазон пути переводит абсолютную позу
в `OUT_OF_GRAPH`, если организаторы не зададут переход на следующий сегмент графа.

## 7. Публикация `nav_msgs/msg/Odometry`

При валидной абсолютной оценке:

```text
header.frame_id = "map"
child_frame_id  = "base_link"
pose.position   = Pathgraph(x, y, z) с учётом lever arm
pose.orientation = quaternion(yaw=tang, pitch≈atan(grade), roll=0)
twist.linear.x  = оценённая продольная скорость, м/с
```

До подтверждения контракта безопаснее публиковать только yaw и оставить pitch/roll
нулевыми: pose `base_link` и высотный datum ещё требуют согласования.

Ковариацию нельзя просто копировать из одномерного состояния. Продольную дисперсию
`sigma_s²` следует повернуть в XY вдоль касательной:

```text
t = [cos(yaw), sin(yaw)]
P_xy = sigma_s² * t*tᵀ + sigma_cross² * n*nᵀ + P_map
```

`sigma_cross` и `P_map` должны отражать неопределённость выбора пути и самой карты.
При `AMBIGUOUS` или `OUT_OF_GRAPH` абсолютная pose должна быть явно недействительной
или иметь согласованную большую ковариацию; конкретное поведение надо подтвердить у
организаторов.

## 8. Использование геометрии в динамической модели

Pathgraph полезен не только для визуализации:

- `grade` позволяет добавить известную часть ускорения `-g*sin(theta)`;
- `curvature` можно использовать как признак дополнительного сопротивления в кривой;
- направленный `tang` позволяет получить знаковую GNSS-скорость проекцией velocity на
  касательную;
- `s` позволяет сравнивать drift вдоль пути и cross-track ошибку отдельно.

Высоту и кривизну нельзя подавать в модель без фильтрации и проверки на train/validation:
численное дифференцирование `z` даёт выбросы уклона, а эффект кривизны может быть мал
по сравнению с неизвестными сопротивлениями.

## 9. Последовательность реализации

### P0 — аналитический загрузчик

- загрузить оба JSON и сформировать DataFrame `route_id, point_index, s, x, y, z,
  yaw, curvature, grade`;
- построить план, профиль высоты, кривизны и расстояния между путями;
- добавить тесты структуры и численных инвариантов.

### P1 — проекция truth

- реализовать конфигурируемое WGS84 → Pathgraph;
- спроецировать GNSS master/rover на сегменты;
- сохранить `s`, cross-track, heading error, match status;
- сформировать coverage report по каждому bag.

### P2 — библиотечный runtime

- реализовать `PathGraph.pose_at` и `PathGraph.project`;
- добавить пространственный индекс;
- добавить параметры `route_id`, `initial_s`, пороги match;
- тестировать точки, середины сегментов, концы и `OUT_OF_GRAPH`.

### P3 — ROS

- добавить bootstrap от GNSS как строго опциональный режим;
- преобразовать `delta_s` оценивателя в `map → base_link`;
- публиковать route/match diagnostics;
- проверить частоту, timestamp и исчезновение GNSS.

### P4 — модель и оценка

- добавить signed GNSS truth по касательной Pathgraph;
- проверить grade feed-forward и curvature feature через ablation;
- считать along-track RMSE, final drift, cross-track и graph coverage;
- не включать вне-графовые точки в ошибку Pathgraph без отдельной маркировки.

## 10. Критерии готовности

1. Оба файла загружаются и проходят валидацию без ручного переименования.
2. `pose_at(s)` непрерывен и точно возвращает концы пути.
3. `project(pose_at(s))` восстанавливает `s` в заданном допуске.
4. Два соседних направления не путаются при наличии heading.
5. GNSS основного маршрута имеет малый cross-track, а депо получает `OUT_OF_GRAPH`.
6. При работе без GNSS после bootstrap выход зависит только от разрешённых внутренних
   сигналов и сохранённого initial state.
7. Выход за начало или конец графа не маскируется валидной крайней точкой.
8. Координатные параметры и route ID видны в конфигурации и startup log.

```text

  → estimator delta_s
  → Pathgraph pose
  → nav_msgs/Odometry
```
