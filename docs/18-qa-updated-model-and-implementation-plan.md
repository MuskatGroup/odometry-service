# План дальнейшей разработки после Q&A

Дата: 25 сентября 2026.

Документ объединяет:

- текст технических требований и ожидаемых артефактов;
- уточнения Q&A о трамвае «Львёнок», `base_link`, массе и системе координат;
- фактический аудит 122 выданных rosbag;
- текущее состояние `odometry_core`, ROS-ноды и аналитических инструментов.

## 1. Краткий ответ: правильно ли понята задача

В основном — да. GNSS нужен для построения офлайн-эталона, идентификации параметров и
оценки качества. В рабочем режиме оцениватель должен выдавать скорость и положение по
разрешённым внутренним сигналам:

- положению контроллера;
- скорости передней тележки;
- скорости задней тележки;
- внутреннему состоянию собственной причинной модели.

Однако задача **не сводится к обучению одного end-to-end ML-классификатора** и не позволяет
честно определить физическую причину каждой ошибки. В данных нет отдельных меток погоды,
массы пассажиров, уклона, износа колёс, кривизны пути или коэффициента сцепления.

Поэтому целевая архитектура должна:

1. идентифицировать номинальную нелинейную динамику `контроллер → ускорение → скорость`;
2. сравнивать модельный прогноз с двумя колесными каналами;
3. выявлять недостоверность каждого канала;
4. уменьшать вес подозрительных измерений;
5. оценивать суммарное неизвестное возмущение, не выдавая его за точно распознанную
   погоду, массу или уклон;
6. продолжать причинный расчёт без GNSS;
7. честно увеличивать неопределённость и объявлять деградацию при длительной
   ненаблюдаемости.

Рекомендуемая стратегия — **гибридная модель**: физически интерпретируемый наблюдатель
с идентифицированными таблицами/коэффициентами и, только при доказанном выигрыше,
небольшая ML-модель остатка или классификатор доверия к колёсам.

## 2. Что подтверждено

### 2.1. Геометрия трамвая

По Q&A:

| Параметр | Значение |
|---|---:|
| Модель | «Львёнок» |
| Расстояние между центрами тележек | 7,550 м |
| Масса пустого трамвая | 27 500 кг |
| Оси `base_link` | `x` вперёд, `y` влево, `z` вверх |
| Начало `base_link` | центр передней тележки на уровне верхней части рельса |

Фраза «400–500 мм от носа» должна быть подтверждена организаторами числом и схемой.
Для трамвая такого размера возможна ошибка конспекта, например 4–5 м. До подтверждения
это значение нельзя зашивать в геометрию.

Расстояние 7,55 м полезно для геометрии кузова и преобразований между точками тележек,
но двух скалярных скоростей тележек недостаточно для прямого определения yaw или
кривизны: нет отдельных левых и правых колёс.

### 2.2. Фактические данные

Во всех 122 bag объявлены только семь топиков:

- три разрешённых входа `/vehicle/*`;
- четыре GNSS-топика `/sensing/gnss/*` для truth/инициализации.

Топиков `localization`, `kinematic_state`, `/tf`, `/odom`, IMU, карты или состояния
тягового привода в выданных bag нет.

GNSS полностью отсутствует в 35 bag. Ещё один bag содержит только rover. Следовательно,
пайплайн обязан поддерживать три режима:

1. полный GNSS truth для обучения и метрик;
2. GNSS только в начале для выставки;
3. полное отсутствие GNSS с относительной одометрией или заданным initial state.

### 2.3. Критическое уточнение единиц колёс

README и комментарий в `VelocitySensor.msg` называют поле `velocity` скоростью в м/с.
На Q&A прозвучало, что колесная одометрия передаётся в км/ч. Фактические данные
поддерживают именно версию Q&A:

| Bag | Медиана `wheel_raw / GNSS_mps` | Коэффициент `GNSS_mps / wheel_raw` |
|---|---:|---:|
| `30618_01f73500` | 3,594 | 0,2781 |
| `30639_0be558e2` | 3,586 | 0,2788 |

`1 / 3.6 = 0,2778`. Максимум raw около 53 также физически правдоподобен как 53 км/ч,
но не как 53 м/с.

**Рабочее решение:** считать raw-поле колёс км/ч и выполнять `v_mps = raw / 3.6` на
границе `odometry_io`. До письменного подтверждения организаторов сохранить параметр
`wheel_velocity_unit`, логировать выбранную единицу и сделать integration test на
отношение к GNSS.

Текущая аналитика и временные профили, где raw называется `velocity_mps`, должны быть
исправлены. Иначе ядро получает скорость, завышенную примерно в 3,6 раза, а калибровка
EKF теряет физический смысл.

## 3. Что означает `/localization/kinematic_state`

Наиболее вероятно, на Q&A имелся в виду Autoware-топик:

```text
/localization/kinematic_state
```

В актуальной документации Autoware этот топик имеет тип `nav_msgs/msg/Odometry` и
содержит pose и twist текущего автомобиля. Это согласуется с упоминанием декартовой
позиции и скорости, но **не отменяет письменный контракт датасета**, где однозначно
требуется непрерывно публиковать:

```text
/result/velocity  tram_vehicle_msgs/msg/VelocitySensor
/result/position  nav_msgs/msg/Odometry
```

Текущее решение по реализации:

- обязательно реализовать `/result/velocity` и `/result/position`;
- не подписываться на `/localization/kinematic_state` и не использовать его как вход;
- конфигурируемый дополнительный alias `/localization/kinematic_state` добавлять только
  если организаторы письменно подтвердят, что он также требуется;
- единый объект результата внутри ноды, чтобы три публикации не расходились.

Это не блокирует разработку обязательных `/result/*`. У организаторов остаётся один
уточняющий вопрос: является ли упомянутый на Q&A `/localization/kinematic_state`
дополнительным выходом участника; если да, нужны его точное имя и тип.

## 4. Pathgraph, MGRS и положение

Организаторы предоставили два направленных pathgraph:

| Маршрут | Точек | Длина по XY | Медианный шаг |
|---|---:|---:|---:|
| Таллинская → Щукинская | 4 709 | 4 707,96 м | ≈ 1,00 м |
| Щукинская → Таллинская | 4 710 | 4 708,34 м | ≈ 1,00 м |

Каждый JSON содержит массив `points` и один элемент `paths` с последовательным
`point_indices`. Точка содержит `x`, `y`, `z`, `tang`, `curv`. Проверка чисел показывает:

- `x/y/z` заданы в метрах в локальной декартовой системе;
- `tang` — направление касательной в радианах; перед использованием его нужно
  нормализовать через `atan2(sin(tang), cos(tang))`;
- `curv` согласуется с `d(tang)/ds` и имеет размерность `1/м`;
- два файла описывают не одну линию в обратном порядке, а два соседних пути с типичным
  поперечным расстоянием около 3,7 м;
- по `z` можно получить уклон, но производную `dz/ds` необходимо сглаживать.

Рабочая гипотеза системы координат подтверждена сопоставлением с GNSS: преобразование
WGS84 в UTM zone 37N с последующим вычитанием `300000` из easting и `6100000` из
northing совмещает треки с Pathgraph. Это похоже на локальные координаты 100-км MGRS
ячейки. Точный `mgrs_grid`, vertical datum и правила системы оценки всё ещё нужно получить
письменно; константы нельзя прятать в коде.

Pathgraph закрывает прежнюю проблему ненаблюдаемости поворотов. Продольная модель
оценивает одномерную координату `s`, а слой геометрии преобразует её в позу:

```text
u, wheel_front, wheel_rear
        │
        ▼
longitudinal observer → s, v, a, uncertainty
        │
        ▼
track/path projection → MGRS x, y, z, yaw
        │
        ▼
nav_msgs/Odometry (map → base_link)
```

Начальную пару `(route_id, s0)` надо определять по стартовой GNSS-позиции и направлению
движения либо получать от стенда. Нельзя выбирать только ближайшую вершину: нужен поиск
ближайшего сегмента с проекцией на него и проверкой направления касательной. Далее
оцениватель интегрирует `delta_s`, а Pathgraph интерполирует `x/y/z/yaw/curvature`.

Сопоставление нескольких длинных bag показало, что большая часть движения попадает на
граф с медианной ошибкой менее 0,5 м, но в начале или конце некоторых записей есть
участки в сотнях метров от него — вероятно, депо и подъездные пути. Поэтому обязателен
режим `OUT_OF_GRAPH`: запрещено молча проецировать такую позицию на ближайший конец
маршрута. При выходе за покрытие система должна либо продолжать относительную
одометрию с недействительной абсолютной позой, либо перейти в согласованный со стендом
degraded-режим.

Полный количественный аудит и контракт загрузчика приведены в
[`19-pathgraph-audit-and-integration.md`](19-pathgraph-audit-and-integration.md).

## 5. Построение ground truth

### 5.1. Скорость

Необходимо сохранить GNSS-вектор `linear.x/y/z`, а не использовать только его модуль.

Порядок:

1. синхронизировать master и rover по `header.stamp`;
2. проверить frame и ориентацию компонентов;
3. построить гладкую траекторию/касательную пути;
4. проецировать GNSS-вектор на касательную, получая знаковую продольную скорость;
5. использовать модуль горизонтальной скорости только как диагностический baseline;
6. фильтровать невалидный GNSS status и разрывы, не превращая их в нули.

### 5.2. Положение

Порядок:

1. преобразовать `NavSatFix` WGS84 в согласованную MGRS-систему;
2. определить, где физически находятся master и rover;
3. оценить/получить их lever-arm относительно `base_link`;
4. преобразовать координаты антенн в truth позиции `base_link`;
5. спроецировать truth на pathgraph и вычислить `s`, along-track и cross-track;
6. не усреднять master и rover до выяснения их геометрии.

Одного определения начала `base_link` недостаточно: нужны координаты обеих GNSS-антенн
в `base_link`. Иначе сохранится постоянное смещение позиции.

### 5.3. Ускорение

Ускорение для идентификации модели строится как производная сглаженной GNSS-скорости.
Сглаживание допустимо для офлайн-метки, но признаки runtime-модели должны оставаться
причинными и не использовать будущие отсчёты.

## 6. Что можно и нельзя распознать по данным

| Явление | Что реально доступно | Решение |
|---|---|---|
| Буксование при тяге | Колесо быстрее GNSS/model, рост при `u>0` | Псевдометка offline, residual/gate runtime |
| Юз при торможении | Колесо медленнее GNSS/model при `u<0` | Псевдометка offline, residual/gate runtime |
| Freeze датчика | Неизменное значение при динамике другого канала/model | Явный детектор |
| Dropout/запаздывание | Timestamp и отсутствие свежего сообщения | Явный детектор |
| Разногласие тележек | `v_front - v_rear` | Поканальное доверие и голосование |
| Нелинейность привода | `u`, `v_truth`, `a_truth`, задержка | Идентифицируемая таблица/функция |
| Различия трамваев | ID 30618/30639 и сессии | Общая модель + профиль vehicle ID |
| Масса пассажиров | Прямой метки нет | Эффективный gain/возмущение, не класс массы |
| Уклон | Высота Pathgraph даёт приближение `dz/ds` | Сглаженный feed-forward + остаточное возмущение |
| Погода/сцепление | Нет погоды и прямой силы сцепления | Режим низкого доверия, не название погоды |
| Износ колёс | Нет радиуса/пробега/метки износа | Медленный scale/bias колёсного канала |
| Кривой участок | Есть `tang` и `curv` Pathgraph | Геометрия выхода и признак сопротивления в кривой |

Нельзя обучить достоверный многоклассовый классификатор причин
`weather/slope/mass/wear` без дополнительных меток. Можно обучить более честные классы
наблюдаемого состояния канала:

```text
normal / positive slip / braking slide / frozen / dropout / inconsistent / unknown
```

## 7. Целевая математическая модель

### 7.1. Состояние

Минимальное состояние текущего EKF уже близко к нужному:

```text
x = [s, v, a_act, d]
```

где:

- `s` — along-track расстояние, м;
- `v` — продольная скорость `base_link`, м/с;
- `a_act` — ускорение привода/тормоза после динамического лага;
- `d` — объединённое медленное возмущение: уклон, масса, сопротивление и ошибка модели.

После стабильной калибровки можно проверить расширение:

```text
x = [s, v, a_act, d, b_front, b_rear]
```

где `b_front/rear` — медленные scale/bias состояния. Не добавлять их до анализа
наблюдаемости и устойчивости.

### 7.2. Привод

Начальная идентифицируемая форма:

```text
tau * da_act/dt = a_cmd(u, v, vehicle_id) - a_act
```

`a_cmd` лучше сначала задать таблицей по дискретной позиции контроллера и диапазону
скорости. Для тяги и торможения используются разные таблицы. Затем сравнить с
параметрической формой текущего `ModelConfig`.

### 7.3. Продольная динамика

```text
ds/dt = v
dv/dt = a_act - c0*sign(v) - c1*v - c2*v*abs(v) + d
dd/dt = process_noise
```

Масса 27 500 кг используется как номинальная физическая константа в документации, но
при отсутствии тягового момента в Н·м параметры `a_cmd` уже содержат эффективное
деление на массу. Не следует одновременно «учить acceleration gain» и свободно менять
массу без ограничения — параметры станут неидентифицируемыми.

### 7.4. Колёсные измерения

После обязательного преобразования км/ч → м/с:

```text
z_front = v + slip_front + bias_front + noise
z_rear  = v + slip_rear  + bias_rear  + noise
```

Для каждого канала рассчитываются:

- innovation относительно модельного `v`;
- физически допустимая производная;
- свежесть и монотонность времени;
- freeze;
- согласованность с другой тележкой;
- режим тяги/торможения;
- накопленный health score и hysteresis повторного захвата.

## 8. Нужно ли сейчас обучать ML

Не начинать с нейросети. Сначала необходимы три baseline:

1. `median(front, rear) / 3.6` с интегрированием;
2. чистый прогноз идентифицированной модели по контроллеру;
3. текущий robust EKF после исправления единиц и калибровки.

Только после честного сравнения добавить один ML-кандидат:

- небольшой gradient boosting/MLP для коррекции `a_cmd` или предсказания model residual;
- либо классификатор доверия к каждому колесу;
- признаки только из причинного окна разрешённых входов;
- GNSS используется только как target/pseudo-label при офлайн-обучении;
- артефакт модели фиксируется в репозитории и работает без интернета;
- runtime укладывается в 2 CPU, 0,5 ГБ и 100 мс.

ML принимается, только если выигрывает на полностью отложенных bag обоих трамваев и не
ухудшает отказоустойчивость. Иначе табличная модель и EKF — более сильная конкурсная
история благодаря интерпретируемости.

## 9. Разбиение данных и отсутствие leakage

Запрещено случайно делить отдельные строки. Нужно:

1. подтвердить кандидатов в дубликаты хешами `.db3`;
2. держать дубликаты только в одной части выборки;
3. делить целыми bag;
4. стратифицировать по ID трамвая, длительности, GNSS availability и режимам движения;
5. оставить отдельный test по `30639`, чтобы проверить перенос с лабораторного на
   линейный трамвай;
6. дополнительно оставить session-holdout внутри каждого ID;
7. не подбирать пороги на test;
8. воспроизводить каждый bag с новым состоянием оценивателя.

Рекомендуемый конфиг:

```text
global model
  + vehicle_id=30618 calibration
  + vehicle_id=30639 calibration
  + default/unknown calibration
```

Параметр `vehicle_id` должен задаваться через ROS parameter/YAML. Не полагаться на имя
bag в production.

## 10. Обновлённая архитектура

```text
ROS input adapter
  ├─ control position (-15..15)
  ├─ front wheel raw (km/h hypothesis) ─┐
  └─ rear wheel raw  (km/h hypothesis) ─┤
                                        ▼
Unit/time/quality normalization (SI, causal ordering)
                                        │
                                        ▼
Drive model + robust adaptive observer
  → s, v, a, disturbance, wheel health, covariance
                                        │
                    ┌───────────────────┴──────────────────┐
                    ▼                                      ▼
Track/MGRS projection                              diagnostics
  → map pose, yaw                                  slip/freeze/mode
                    │
                    ▼
Publishers required by the organizers
  ├─ /result/velocity
  ├─ /result/position
  └─ /localization/kinematic_state (only if confirmed)
```

GNSS bootstrap/truth должен быть отдельным модулем с жёстким режимом:

```text
disabled | initialization_only | offline_truth
```

Так GNSS невозможно случайно использовать как постоянный runtime-вход.

## 12. План реализации

### P0. Закрыть контракт и единицы — немедленно

Ответственные: архитектор + автоматизатор.

1. Отправить организаторам вопросы из раздела 13.
2. Исправить organizer-профили на `unit: km/h` за feature flag.
3. В аналитике переименовать raw в `wheel_velocity_raw` и отдельно вычислять
   `wheel_velocity_mps = raw / 3.6`.
4. Добавить regression test на эмпирический scale около 3,6 в нескольких train bag.
5. Сохранить позицию контроллера одновременно как raw `-15…15` и normalized `-1…1`.

Приёмка: baseline wheels и GNSS имеют масштаб около 1 на валидных участках; выбранная
единица видна в конфиге и startup log.

### P1. Truth pipeline и датасет — первый рабочий поток

Ответственные: DS + автоматизатор.

1. Построить таблицы входов и GNSS truth по `header.stamp`.
2. Реализовать GNSS status/gap validation.
3. Реализовать конфигурируемое WGS84 → локальная MGRS/Pathgraph-система и подтвердить
   `mgrs_grid` у организаторов.
4. Оценить master/rover baseline и запросить antenna extrinsics.
5. Спроецировать GNSS на сегменты обоих направленных графов и построить `route_id`,
   signed speed, acceleration, path coordinate `s`, cross-track и `OUT_OF_GRAPH`.
6. Построить сглаженные профили высоты/уклона и проверить их применимость в модели.
7. Сформировать session split без дубликатов.
8. Выделить offline pseudo-labels slip/slide/freeze/dropout.

Приёмка: для каждого test bag автоматически формируется truth coverage report; отсутствие
GNSS даёт `metrics unavailable`, а не нули.

### P2. Идентификация модели — второй рабочий поток

Ответственный: DS.

1. Оценить лаг `tau` между изменением контроллера и GNSS acceleration.
2. Построить `a_cmd(position, speed, vehicle_id)` отдельно для тяги и торможения.
3. Оценить сопротивление и допустимый диапазон disturbance.
4. Калибровать process/measurement noise EKF на train/validation.
5. Проверить disturbance adaptation с заморозкой при недостоверных колёсах.
6. Сравнить три baseline и только затем residual ML.

Приёмка: таблица метрик по отложенным bag показывает вклад каждой части через ablation.

### P3. Robust wheel fusion — параллельно с P2

Ответственный: разработчик-архитектор.

1. Перекалибровать innovation gates после исправления единиц.
2. Разделить positive slip и braking slide по знаку команды/residual.
3. Проверить freeze, dropout, spike, timestamp reversal и reacquisition.
4. Публиковать health каждого канала и итоговый mode.
5. Ограничить обновление параметров только доверенными режимами.

Приёмка: на искусственных и найденных реальных инцидентах оценка лучше wheel median и не
делает drift blow-up.

### P4. Координаты и контракт испытательного стенда ROS

Ответственный: разработчик-архитектор; DS предоставляет truth transform.

1. Добавить конфигурацию геометрии «Львёнка» и `vehicle_id`.
2. Реализовать загрузчик выданного JSON, его валидацию и предварительный расчёт
   накопленной координаты `s` и сглаженного уклона.
3. Реализовать `track_geometry` интерфейс:
   `(route_id, s) → x,y,z,yaw,curvature,grade`.
4. Реализовать GNSS bootstrap/map matching по ближайшему сегменту с учётом направления,
   параметрами `route_id`, `initial_s` и явным состоянием `OUT_OF_GRAPH`.
5. Публиковать `/result/velocity` и `/result/position` ≥ 20 Гц.
6. Заполнять `header.stamp`, `frame_id=map`, `child_frame_id=base_link`, pose, quaternion,
   twist и covariance.
7. Проецировать продольную неопределённость в XY вдоль касательной и отдельно учитывать
   неопределённость графа/поперечного положения.
8. Добавить `/localization/kinematic_state` как alias только после подтверждения.
9. GNSS initialization выключать после конфигурируемого bootstrap window.

Приёмка: `ros2 topic info/echo/hz` совпадает с контрактом; временные метки результатов находятся в
допуске 50 мс; нода продолжает работать после исчезновения GNSS.

### P5. Испытания и сдача

Ответственные: автоматизатор + два full-stack-разработчика.

1. Batch-run всех bag с фиксированными split/config/model hash.
2. Метрики: speed MAE/RMSE/bias/p95, position final drift %, along-track RMSE/MAX,
   availability, recovery time, latency/hz/RAM/CPU.
3. Отчёты отдельно по vehicle ID, GNSS availability и режимам.
4. Dashboard читает готовые отчёты и не входит в realtime-контур.
5. Проверить `colcon build` и запуск без внешнего интернета.
6. Подготовить сценарий демонстрации: normal → slip → GNSS loss → recovery.

Приёмка: один документированный запуск на чистом окружении воспроизводит выходные топики,
метрики и графики.

## 14. Распределение команды

| Участник | Независимый участок | Результат |
|---|---|---|
| Data Scientist | Truth, split, system identification, EKF/ML calibration | model config + notebook + metrics |
| Python-автоматизатор | Конвертер, batch evaluator, pseudo-labels, regression/failure tests | воспроизводимый pipeline |
| Архитектор | Units/time, ROS integration, MGRS/path interface, vehicle profiles | рабочие ROS-ноды |
| Full-stack A | API каталога запусков и импорт отчётов | backend без влияния на realtime |
| Full-stack B | Графики truth/estimate/incidents и demo screen | интерфейс демонстрации |

Контракты между потоками фиксируются заранее:

- DS получает SI DataFrame и не читает CDR самостоятельно;
- core принимает только `ControlSample` и `WheelSample` в SI;
- geometry получает `s` и возвращает map pose;
- evaluator использует GNSS только вне runtime estimator;
- web получает сохранённые telemetry/report, не вызывает estimator в цикле.

## 15. Решение для ближайшего следующего шага

До ответа организаторов можно безопасно выполнить:

1. исправление km/h → m/s;
2. построение корректного GNSS speed truth;
3. session split и дедупликацию;
4. wheel-median baseline;
5. идентификацию `a_cmd(position, speed, vehicle_id)`;
6. калибровку текущего EKF;
7. тест GNSS disappearance после первых секунд;
8. загрузчик Pathgraph, map matching и публикацию `/result/*` в его системе координат;
9. явное обнаружение участков `OUT_OF_GRAPH`.

Нельзя окончательно фиксировать до ответа:

- окончательную трактовку абсолютного MGRS и vertical datum;
- трансформацию GNSS → `base_link`;
- обязательность `/localization/kinematic_state`;
- поведение абсолютной позиции вне покрытия Pathgraph;
- финальный launch/config испытательного стенда.

## 16. Источники для трактовки спорных терминов

- В документации Autoware `/localization/kinematic_state` указан как
  `nav_msgs/msg/Odometry`:
  <https://autowarefoundation.github.io/autoware_tools/main/planning/planning_debug_tools/>.
- Формат конфигурации MGRS в Autoware требует `projector_type`, vertical datum и
  `mgrs_grid`:
  <https://autowarefoundation.github.io/autoware.universe_planning/main/map/map_projection_loader/>.

Это подтверждает рабочую интерпретацию терминов, но не заменяет конкретный контракт
организаторов хакатона.
