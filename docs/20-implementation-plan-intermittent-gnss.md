# План реализации с периодическими GNSS-коррекциями

Дата: 26 сентября 2026.

## 1. Зафиксированные решения

### 1.0. Координаты и геометрия

- Фиксированный MGRS reference grid: `37UCB`.
- Непрерывные координаты:
  `x = UTM37N.easting - 300000`, `y = UTM37N.northing - 6100000`.
- Переход в соседний квадрат не применяет modulo `100000`; `x` может быть больше
  `100000`.
- `/result/position` — положение `base_link` на оси передней тележки, на уровне контакта
  колеса и рельса.
- Задняя тележка: `[-7.55, 0, 0]` в `base_link`.
- Master: `[-9.873, 0, 3]`, rover: `[2.563, 0, 3]` в `base_link`.
- Две антенны образуют продольный baseline `12.436 м` и позволяют получить yaw кузова.

Полные формулы и тестовые значения приведены в
[`21-coordinate-frame-and-gnss-extrinsics.md`](21-coordinate-frame-and-gnss-extrinsics.md).

### 1.1. Два режима работы

Поддерживаем два режима, выбираемых до запуска ROS-ноды.

#### `route_start`

- GNSS не используется.
- Обязателен направленный `route_id`.
- `route_id` означает старт из первой точки соответствующего JSON.
- `s0 = 0`, начальная позиция и yaw берутся из первой точки Pathgraph.
- Скорость и приращение `s` вычисляются только по контроллеру, колёсам и модели.

#### `gnss_corrected`

- Первые валидные GNSS-сообщения задают `route_id` и `s0`.
- После инициализации модель продолжает причинный прогноз.
- Любые последующие валидные GNSS-сообщения могут корректировать накопленный drift.
- При исчезновении GNSS нода автоматически продолжает работу по модели.
- Возвращение GNSS не вызывает жёсткого скачка координаты: используется gated Kalman
  update и диагностика принятия/отклонения коррекции.

GNSS здесь является разрешённым редким абсолютным измерением, а не обязательным
непрерывным входом. Отсутствие GNSS не должно останавливать публикацию результата.

### 1.2. Единицы колёс

Организаторы подтвердили, что сырые `VelocitySensor.velocity` передаются в км/ч. На границе
`odometry_io` всегда выполняется:

```text
wheel_mps = wheel_raw_kmh / 3.6
```

Коэффициент `3.6` не следует добавлять как свободное состояние EKF:

- это известное преобразование единиц, а не параметр физической модели;
- в `route_start` без GNSS такой коэффициент ненаблюдаем;
- свободный scale будет конкурировать со скоростью, disturbance и параметрами тяги;
- при проскальзывании он может ошибочно «обучиться» на неисправном колесе.

Позднее допустимо добавить отдельные ограниченные коэффициенты калибровки колёс
`lambda_front/rear` около `1.0`, отражающие радиус/износ. Они обновляются только при
валидном GNSS, согласованных колёсах и отсутствии slip, а при потере GNSS замораживаются.

## 2. Проверка выводов аналитика

Независимый пересчёт текущими инструментами дал:

| Bag | Медиана raw/GNSS | RMSE после `/3.6` | Max разности колёс raw | Max после `/3.6` |
|---|---:|---:|---:|---:|
| `30618_af7496f0` | 3,5958 | 0,161 м/с | 0,588 км/ч | 0,163 м/с |
| `30618_2050d396` | 3,5965 | 0,086 м/с | 15,382 км/ч | 4,273 м/с |
| `30639_e4379d7f` | 3,6258 | 0,134 м/с | 3,135 км/ч | 0,871 м/с |
| `30618_27e994fc` | 3,5739 | 0,127 м/с | 0,798 км/ч | 0,222 м/с |

Выводы:

1. Гипотеза о смешанных единицах не подтверждается. Малый bias короткого bag не
   доказывает м/с: bias зависит от средней скорости.
2. Коэффициент `3.6` подтверждён и на двух трамваях.
3. `30618_2050d396` — сильный реальный кандидат slip/disagreement: после перевода
   остаётся 18 синхронных отсчётов с разностью тележек более `2 м/с`.
4. `30639_e4379d7f` — полезный слабый кейс, но не второй сильный slip по порогу `2 м/с`.
5. Имена `velocity_mps` и `wheel_disagreement_mps` в текущей аналитике вводят в
   заблуждение: до нормализации это raw км/ч.
6. `30618_27e994fc` длится около 31,6 минуты и подходит для проверки drift.
7. `30639_e4379d7f` длится около 23,9 минуты, но rover GNSS присутствует только на части
   записи; это хороший тест исчезновения и появления GNSS.

Перед назначением метки «проскальзывание» нужно построить окно инцидента
`30618_2050d396`, проверить временное выравнивание, команду контроллера и GNSS. Большое
расхождение колёс является наблюдаемой аномалией, но само по себе ещё не доказывает её
физическую причину.

## 3. Целевая схема

```text
/vehicle/front_bogie_velocity ─┐
/vehicle/rear_bogie_velocity  ─┼─► SI normalization (/3.6) ─┐
/vehicle/driver_position_cmd  ─┘                            │
                                                           ▼
                                               robust longitudinal EKF
                                               state [delta_s, v, a, d]
                                                           │
GNSS fix/velocity (optional)                               │
       │                                                   │
       ▼                                                   │
validation → WGS84/Pathgraph → map matching → [s,v] updates┤
                                                           │
Pathgraph(route_id, s0 + delta_s) ◄────────────────────────┘
       │
       ├─► /result/velocity
       └─► /result/position
```

Разделение ответственности:

- ROS/IO знает исходные сообщения и единицы;
- geometry знает WGS84, Pathgraph, route и проекцию на сегмент;
- core получает только SI-события и along-track corrections;
- evaluator строит GNSS reference с оценкой качества и не вмешивается в состояние estimator;
- API/web только отображают сохранённую телеметрию.

## 4. Контракт GNSS-коррекции

В core не передаются latitude/longitude. Geometry формирует два скалярных измерения:

```python
AlongTrackPositionCorrection(stamp_ns, route_id, s_m, variance_m2, source)
LongitudinalVelocityCorrection(stamp_ns, v_mps, variance_m2ps2, source)
```

EKF применяет:

```text
position: Hs = [1, 0, 0, 0]
velocity: Hv = [0, 1, 0, 0]
```

Коррекция принимается только если:

- GNSS status и координаты валидны;
- timestamp монотонен и не слишком стар;
- covariance конечна и находится в допустимом диапазоне;
- точка попала на текущий route с допустимым cross-track;
- heading согласуется с направлением route, когда скорость достаточна;
- innovation проходит отдельный NIS-gate;
- route после первичной привязки не переключается на соседний путь от одного fix.

Названия master и rover не задают приоритет: организаторы трактуют их как антенну 1 и
антенну 2. При наличии обеих они используются симметрично для расчёта `base_link`, yaw
и контроля baseline. При наличии одной включается single-antenna fallback с повышенной
covariance. Каждая принятая и отклонённая коррекция получает reason code.

После длительного разрыва GNSS повторный захват требует нескольких согласованных fix.
Жёстко присваивать `s = s_gnss` нельзя: это создаст скачок `/result/position`.

## 5. Что отсутствует в текущей реализации

| Область | Сейчас | Требуется |
|---|---|---|
| Organizer input | В профилях только демонстрационные `/external/*` | Реальные три `/vehicle/*`, km/h → m/s |
| GNSS | Нет runtime-адаптера и событий core | Валидация, проекция, position/velocity corrections |
| Pathgraph | Есть аналитический загрузчик | Runtime API `project()` и `pose_at()` без pandas |
| EKF | Обновление скорости только колёсами | Отдельные gated updates `s` и `v` от GNSS |
| Инициализация | Только `initial_s_m` | `route_start` и `gnss_corrected` state machine |
| ROS output | `/odometry/*`, позиция `x=s,y=z=0` | Обязательные `/result/velocity`, `/result/position` |
| Frame | `odom_1d → tram_1d` | Согласованный `map → base_link` |
| Аналитика units | Raw называется `velocity_mps` | Явные `wheel_velocity_raw_kmh` и `wheel_velocity_mps` |
| Модель | Стартовые `kt/kb/c1/c2` | Идентификация на train, фиксация config artifact |

## 6. План реализации

### P0. Исправить входные единицы и аналитические имена

Ответственные: архитектор + автоматизатор.

1. Добавить organizer ROS profile для трёх `/vehicle/*`.
2. Указать колесам `unit: km/h`; выход `WheelSample.speed_mps` оставить строго SI.
3. Переименовать raw-колонки аналитики и пересчитать derived SI-колонки.
4. Исправить `duration_s` и проверку bool `has_fix` в аналитическом отчёте.
5. Добавить тесты `0 → 0`, `3.6 → 1`, `36 → 10`, оба wheel ID.
6. Добавить dataset regression: медиана `wheel_mps/GNSS_mps` близка к `1`, а не `3.6`.

Приёмка: ни один компонент после `odometry_io` не видит км/ч; startup log явно пишет
выбранную входную единицу.

### P1. Подготовить production Pathgraph

Ответственный: архитектор.

1. Вынести runtime-загрузчик из `dataset/analysis` в библиотечный модуль без pandas.
2. Реализовать `pose_at(route_id, s)` с интерполяцией `x/y/z/yaw/curvature/grade`.
3. Реализовать `project(x,y,yaw?)` на ближайший сегмент, а не вершину.
4. Добавить spatial index или локальный поиск, измерить worst-case latency.
5. Реализовать `MATCHED/AMBIGUOUS/OUT_OF_GRAPH`.
6. Зафиксировать ASCII route IDs и проверку первой точки для `route_start`.

Приёмка: `project(pose_at(s))` восстанавливает route и `s`; соседние пути не путаются
при наличии heading; выход за границы не зажимается.

### P2. Добавить GNSS truth и correction pipeline

Ответственные: DS + архитектор.

1. Реализовать подтверждённое WGS84 → UTM 37N → непрерывные координаты относительно
   `37UCB` без modulo `100000`.
2. Валидировать `NavSatFix.status`, covariance, finite values, gaps и timestamps.
3. Синхронизировать master/rover; проверить baseline `12.436 м` и вычислить yaw кузова.
4. Компенсировать TF антенн и получить позицию `base_link` до map matching.
5. Проецировать `base_link` fix в `route_id/s/cross_track`.
6. Проецировать GNSS velocity на продольную ось/касательную и получать signed `v`.
7. Реализовать симметричный dual-antenna расчёт и single-antenna fallback при потере
   одного приёмника.
8. Ввести отдельные domain-типы position/velocity correction.
9. Сохранять полный audit trail коррекций для отчёта.

Приёмка: для выбранных bag формируется таблица accepted/rejected corrections с причиной;
удаление всех GNSS сообщений не ломает `route_start`.

### P3. Расширить EKF периодическими коррекциями

Ответственный: DS.

1. Обобщить scalar update EKF для произвольного `H`.
2. Добавить position update по `s` и отдельный GNSS velocity update.
3. Настроить разные variance/gates для wheel, GNSS position и GNSS velocity.
4. Реализовать reacquisition после длительного GNSS gap.
5. Замораживать disturbance/будущую wheel-scale adaptation на сомнительных коррекциях.
6. Публиковать `last_gnss_age`, accepted/rejected counts и reason codes.
7. Не добавлять wheel scale в state до ablation, подтверждающего пользу после `/3.6`.

Приёмка: редкая валидная коррекция уменьшает drift без скачка; выброс GNSS не утягивает
состояние; после исчезновения GNSS прогноз продолжается.

### P4. Идентифицировать продольную модель и slip policy

Ответственные: DS + автоматизатор.

1. На чистых участках оценить лаг привода и `a_cmd(position, v, vehicle_id)`.
2. Начать с раздельной линейной/табличной тяги и торможения, затем сравнить
   `c1*v + c2*v*abs(v)`.
3. Использовать grade Pathgraph как проверяемый feed-forward, а не смешивать его с тяговым gain.
4. Разобрать окно `30618_2050d396`: controller, оба колеса после `/3.6`, GNSS, residual.
5. Создать наблюдаемые классы `positive_slip`, `braking_slide`, `disagreement`, `unknown`.
6. Проверить channel gate, median, model-only fallback и reacquisition.
7. Использовать `30639_e4379d7f` как слабую аномалию/частичный GNSS, не как доказанный
   сильный slip.

Приёмка: ablation показывает выигрыш над wheel median на slip bag и отсутствие ухудшения
на чистых bag.

### P5. Реализовать ROS-контракт организаторов

Ответственный: архитектор.

1. Подписаться на реальные `/vehicle/*` и опциональные GNSS-топики.
2. Добавить параметры `initialization_mode`, `route_id`, Pathgraph path, receiver policy.
3. Реализовать state machine `WAITING_FOR_FIX/TRACKING/GNSS_GAP/OUT_OF_GRAPH/INVALID`.
4. Публиковать `/result/velocity` и `/result/position` не реже 10 Гц, целево 50 Гц.
5. Использовать timestamp соответствующего обработанного входа.
6. Публиковать `map → base_link`, quaternion yaw, twist и covariance.
7. Оставить текущие `/odometry/*` только как диагностические топики.

Приёмка: автоматический ROS test проверяет имена, типы, поля, частоту, timestamps и
продолжение работы при исчезновении/возвращении GNSS.

### P6. Честная оценка качества

Ответственный: автоматизатор + DS.

Наборы:

- `30618_2050d396` — сильное wheel disagreement;
- `30618_27e994fc` — длительный drift;
- `30618_af7496f0` — чистый короткий sanity test;
- `30639_e4379d7f` — другой трамвай, частичный rover GNSS;
- bag без GNSS — обязательный `route_start` test.

Эксперименты:

1. GNSS disabled полностью.
2. GNSS только первые 2 секунды.
3. GNSS прорежен, например одна коррекция каждые 30/60/120 секунд.
4. Реальные GNSS gaps.
5. Искусственные выбросы и скачки на соседний путь.

GNSS, поданный в estimator, нельзя одновременно считать независимым reference на том же
timestamp. Отдельной эталонной скорости нет. Для честной оценки использовать withheld
timestamps; для velocity reference — согласованные проекции двух GNSS velocity с
проверкой через производную позиции `base_link`. Колёса не входят в target.

Метрики:

- velocity MAE/RMSE/p95;
- along-track position RMSE и final drift;
- ошибка непосредственно перед каждой GNSS-коррекцией;
- величина скачка результата после коррекции;
- correction acceptance/rejection;
- доступность и длительность model-only;
- latency, частота, CPU и RAM.

## 7. Порядок первых задач

Не начинать одновременно с обучения ML и полной переделки ROS. Первый вертикальный срез:

1. **P0:** корректные км/ч → м/с и organizer profile.
2. **P1:** runtime `pose_at/project` для Pathgraph.
3. **P2-lite:** один receiver → along-track `s/v` correction.
4. **P3-lite:** position/velocity update существующего EKF.
5. **P5-lite:** `/result/velocity` и `/result/position` на одном bag.
6. Прогон с искусственным GNSS gap и возвратом.
7. Только после сквозного результата — идентификация модели и тонкая настройка slip.

Этот срез должен сначала заработать на `30618_af7496f0`, затем на
`30618_2050d396`, после чего — на длинном `30618_27e994fc`.

## 8. Распределение команды

| Участник | Первый независимый участок | Результат |
|---|---|---|
| Архитектор | P0 organizer profile + P1 geometry + ROS wiring | входы, Pathgraph API, рабочая нода |
| Data Scientist | P2 truth/corrections + P3 EKF math + P4 identification | correction API, параметры модели, ablation |
| Python-автоматизатор | dataset regressions + GNSS masking + incident extraction | воспроизводимые тесты и отчёты |
| Full-stack A | расширение API схемы correction diagnostics | хранение новых полей без влияния на runtime |
| Full-stack B | Pathgraph/GNSS/estimate overlay | экран демонстрации drift и коррекции |

Full-stack задачи начинаются после фиксации JSON telemetry schema; до этого они могут
подготовить только отображение существующего Pathgraph.

6. Подтвердить vertical datum: является ли `z` эллипсоидальной высотой
   `NavSatFix.altitude - 3.0 м`. XY и фиксированный квадрат `37UCB` уже подтверждены.

Эти ответы влияют на edge cases, но не блокируют P0, P1 и библиотечную часть P3.
