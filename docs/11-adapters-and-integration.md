# Подключение неизвестного источника: исполняемая заготовка

До начала мероприятия формат эмулятора и тестовых данных неизвестен. Цель — менять источник и его профиль, сохраняя обработку событий, расчет и формат результатов. Существующие проектные документы остаются без изменений; ниже описан отдельный реализованный слой `odometry_io`, а не завершение всего запланированного алгоритма.

## Что уже работает

- Переключение CSV, JSONL, синтетического эмулятора и нормализованной записи через source-конфигурацию.
- Профиль полей, вложенных объектов/массивов, единиц скорости, радиуса колеса, кодировки управления и шкалы времени.
- Настраиваемые каналы скорости и сменные стратегии: медианная оценка либо выбранный канал. Известный агрегат нельзя учитывать вместе с его исходными каналами.
- Наносекундные timestamp без преобразования через float, проверка конечности, дубликатов и конфликтов, ограниченная очередь переупорядочивания.
- Одинаковые временные группы объединяются один раз. Новые разные значения одного канала в одной группе отклоняются как неоднозначные.
- Запись нормализованных пакетов, оценок, конфигураций, хешей исходного файла и отчета. Replay сохраняет группировку доставки и дает тот же результат при одинаковых настройках.
- Независимый синтетический источник с пропусками и искажением канала; отдельный экспорт эталона для офлайн-оценки.

Вычислитель сейчас — **B0 wheel + hold**: последнее объединенное измерение скорости и интегрирование пути. При устаревании скорость сохраняется для диагностики, но `valid=false`. `BASELINE_HOLD` обозначает базовый алгоритм, а не достоверность физической модели. Неопределенность пока не калибрована и передается как `null`. EKF, адаптация и модельный прогноз по ручке еще не реализованы.

## Локальный запуск

Нужен Python 3.10 или новее. Runtime использует только стандартную библиотеку. Проверено на Windows с Python 3.14.6; отдельный прогон на Python 3.10/Ubuntu еще предстоит.

Из корня репозитория в PowerShell:

```powershell
$env:PYTHONPATH = "$PWD\src"
python -m unittest discover -s tests -v
python -m odometry_io --source examples/source-csv.json --output work/run-csv
python -m odometry_io --source examples/source-jsonl.json --output work/run-jsonl
python -m odometry_io --source examples/source-emulator.json --output work/run-emulator
```

Выходной каталог должен быть пустым: существующие результаты не перезаписываются. `work/` в примерах — локальные результаты, их не нужно добавлять в Git. Альтернативно пакет устанавливается через `python -m pip install -e .`, после чего доступна команда `odometry-io`.

`source-*.json` содержит только `format`, `input`, `profile`. Относительные пути разрешаются относительно source-файла. Например, переключение источника не меняет вызываемый вычислитель:

```json
{"format":"csv","input":"input.csv","profile":"profile.json"}
```

Для нового табличного набора достаточно такого source-файла и профиля, если его поля и преобразования покрываются текущим адаптером.

## Профиль и расширение

Рабочие примеры: `examples/profile.json` и `examples/profile-emulator.json`. Профиль имеет версию `adapter-1`; это версия нового слоя ввода, отдельная от проектного контракта в прежних документах.

`timestamp` задает поле, единицу `s/ms/us/ns` и необязательный `offset_ns`. Timestamp передается целым числом, строкой или Decimal; неточное float-время отклоняется. У канала может быть собственное `timestamp_field` в той же шкале. Несинхронизированные часы нужно преобразовать явно в пользовательском адаптере; автоматически они не совмещаются.

Канал задается через `id`, `field`, `unit`; поддержаны `m/s`, `km/h`, `rad/s`, `rpm`. Угловая скорость требует `radius_m`. `valid_field` отражает только пригодность входа. `missing=skip` означает отсутствие отсчета, а не нулевую скорость. Управление нормализуется через `mapping` либо `scale/offset`; неизвестные положения ручки отклоняются. Пути вида `payload.wheels.0.speed` читают вложенные данные.

`fusion.channels` задает используемый набор, `derived_from` у канала обозначает известные производные зависимости. `fusion.strategy` выбирает `median` или `selected_channel` (с полем `channel`). Дисперсия начальной стратегии имеет нижний предел и не делится автоматически на количество каналов. Это не детектор общего проскальзывания; калибровка доверия остается задачей наблюдателя.

Новый транспорт подключается функцией `reader(path)`, возвращающей итератор словарей. Зарегистрировать его можно через `register_reader(name, reader)`. CLI принимает `--plugin my_reader`: это явный импорт доверенного Python-модуля, который регистрирует читатель. Новое имя затем используется в поле `format`. Конфигурационные JSON не исполняют Python-код. Тем же способом `register_strategy` добавляет стратегию слияния.

Если одного отображения полей недостаточно, транспортный адаптер может выдавать пакеты `Event` прямо в `run(...)`. Замена алгоритма производится через аргумент `estimator`, реализующий `ingest(stamp_ns, events)` и `advance_to(stamp_ns)`. Ни источник, ни формат результатов не обязаны зависеть от ROS.

## Replay и проверка качества

```powershell
python -m odometry_io --input work/run-csv/normalized.jsonl --format normalized --profile examples/profile.json --output work/run-replay
python -m odometry_io.emulator --config examples/emulator.json --output work/synthetic
python -m odometry_io --input work/synthetic/input.jsonl --format jsonl --profile examples/profile-emulator.json --truth work/synthetic/truth.jsonl --output work/run-evaluated
```

`--truth` используется только после расчета для независимой оценки. Отчет содержит RMSE скорости и пути на точных совпадениях timestamp, ошибку пути в последней совпавшей точке, число совпадений и ошибки на валидных оценках отдельно. Сложные интервалы с конечным прогнозом не исключаются из общей ошибки. Если совпадений нет, метрики равны `null`. Для разных сеток пока не выполняются интерполяция и временное взвешивание; количество совпадений нужно учитывать при сравнении.

Частота выходной сетки задается `--output-hz`, таймаут скорости — `--speed-timeout-s`, конечное продолжение прогноза — `--tail-s`, окно переупорядочивания — `--reorder-ms`. Лимиты `--max-pending` и `--max-outputs` предотвращают неограниченный рост очереди и случайный огромный прогон при ошибке единиц времени. Кэш дедупликации ограничен: старые повторы после вытеснения отклоняются как поздние, если их время уже закрыто.

## Ограничения и следующее подключение

Файловый runner выполняет детерминированный прогон по времени событий. Для живого источника есть `LiveSession` из `odometry_io.live`: транспорт вызывает `ingest(events)`, независимый таймер вызывает `advance_to(stamp_ns)` даже при полном молчании источника. Все вызовы сериализуются в одном event loop; фоновые callbacks должны передавать события через очередь. Совмещение часов и запуск таймера принадлежат транспортной оболочке. Session хранит ограниченную очередь будущих событий и отмечает поздние; повторный или обратный tick отклоняется. При смене эпохи создается новая session.

Необязательный callback `journal` получает операции доставки и продвижения времени; `replay_actions` воспроизводит те же таймауты и оценки. Пример интеграции:

```python
from odometry_io.live import LiveSession

session = LiveSession(profile, journal=save_action)
# В транспортном callback после нормализации:
session.ingest(events)
# В независимом таймере в той же шкале времени:
frame = session.advance_to(clock_ns)
```

`save_action`, нормализацию внешних сообщений и источник `clock_ns` предоставляет оболочка конкретного стенда. Сетевой сервер и автоматический запуск wall-clock таймера пока не поставляются.

ROS-оболочки, rosbag-декодирование, HTTP/SignalR и web пока отсутствуют. Адаптер конкретных сообщений создается после получения примера. Сначала необходимо проверить единицы, часы, семантику ручки и состав каналов на baseline, затем подключать наблюдатель. Универсальность формата не гарантирует точность на неизвестной физике.

Следующие этапы: транспортная оболочка эмулятора с независимым таймером; модельный baseline и EKF за существующим интерфейсом; оценка на отдельном наборе сценариев; ROS-адаптер после определения внешних типов. Существующие Markdown-файлы не меняются; уточнения этого слоя ведутся здесь.
