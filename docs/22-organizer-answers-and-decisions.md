# Ответы организаторов и принятые решения

Дата: 26 сентября 2026.

## 1. `/result/position`

Ответ: координаты заданы в MGRS, а не в локальной ENU-плоскости с началом в первом GNSS
fix.

Решение:

- использовать подтверждённую непрерывную систему относительно `37UCB`;
- `x = UTM37N.easting - 300000`;
- `y = UTM37N.northing - 6100000`;
- не поворачивать оси относительно UTM/MGRS по направлению стартовой касательной;
- не обнулять координаты в первой точке;
- не применять modulo `100000` при переходе в соседний квадрат.

## 2. Оси и высота

Ответ: `z` — высота, система координат соответствует REP-103 ROS 2.

REP-103 задаёт SI и ориентацию: для географической декартовой системы `x` направлена на
восток, `y` на север, `z` вверх; body frame использует `x` вперёд, `y` влево, `z` вверх.
Он не задаёт однозначно vertical datum конкретного датасета.

Решение:

- публиковать метры и `z` вверх;
- положение относится к `base_link`;
- геометрический offset антенн по z равен `-3.0 м`;
- не применять геоидную поправку без отдельного подтверждения;
- оставить `vertical_datum` явным параметром и проверить контрольный пример по исходному
  `NavSatFix.altitude`.

Официальный REP-103:
<https://github.com/openrobotics/reps/blob/main/_posts/rep-0103.md>.

## 3. Антенны

Ответ: названия `master` и `rover` в этой задаче следует воспринимать как «антенна 1» и
«антенна 2», а не как основной и вторичный эталоны.

Позднее организаторы предоставили TF:

```text
antenna 1 (topic master) = [-9.873, 0, 3] м
antenna 2 (topic rover)  = [ 2.563, 0, 3] м
```

Решение:

- при наличии обеих антенн использовать их симметрично для позиции/yaw и проверки
  baseline `12.436 м`;
- при наличии одной использовать single-antenna fallback с большим covariance;
- не считать одну из них безусловным ground truth;
- хранить topic/source ID, но не присваивать смысл primary/secondary.

## 4. Скорость

Ответ: отдельной эталонной скорости нет. Есть четыре источника измерения:

- передняя тележка;
- задняя тележка;
- GNSS antenna 1 velocity;
- GNSS antenna 2 velocity.

Решение:

- не называть `/sensing/gnss/master/vel` истинной скоростью;
- для офлайн reference использовать согласованный consensus двух GNSS velocity,
  спроецированный на продольную ось/Pathgraph;
- независимо проверять его производной сглаженной позиции `base_link`;
- колёса не включать в обучающий target, иначе slip будет замаскирован и возникнет
  leakage;
- при расхождении GNSS reference помечать метрику недоступной или увеличивать её
  uncertainty;
- запросить у организаторов точную формулу автоматического score `/result/velocity`.

Термин `ground truth speed` в документации означает только построенный reference с
описанной методикой и ограничениями, а не физически безошибочное измерение.

## 5. Время воспроизведения

Ответ: bag можно проигрывать удобным способом; `--clock` не является обязательным
условием организаторов.

Решение:

- алгоритм всегда использует `header.stamp` измерений;
- поддерживать ROS simulated time для воспроизводимых тестов;
- поддерживать live/system time для стенда;
- не делать математику фильтра зависимой от скорости воспроизведения bag.

## 6. Карта и тестовая линия

Ответ: организаторы обещали предоставить карту позднее. После этого был предоставлен
Pathgraph из двух направленных путей.

Решение:

- production использует только выданный Pathgraph/карту;
- GNSS train-данные используются для проверки и калибровки, а не для скрытого построения
  другой карты;
- необходимость работы вне покрытия отмечается `OUT_OF_GRAPH`;
- отдельно требуется подтвердить, что закрытые тесты ограничены покрытием выданной карты.

## 7. Колёсная скорость

Ответ: км/ч подтверждены организаторами.

Решение:

```text
wheel_mps = VelocitySensor.velocity / 3.6
```

Преобразование выполняется один раз на границе IO. Автоматически определять единицы в
EKF не требуется.

## 8. Что осталось неизвестным

1. Формула reference/score для `/result/velocity` при отсутствии эталонного датчика.
2. Vertical datum `z`: эллипсоидальная высота, геоид или иной источник.
3. Гарантируется ли GNSS в начале либо он может впервые появиться в середине.
4. Что публиковать для absolute position до первого fix в `gnss_corrected`.
5. Ограничены ли закрытые тесты покрытием предоставленного Pathgraph.
6. Является ли `/localization/kinematic_state` дополнительным обязательным выходом.
