# Контракты интеграции v0.1

Обновление реализации: [контракты v0.2](../contracts/README.md) добавляют `has_estimate`, `uncertainty_available`, поканальные скорости, историю телеметрии и атомарный ROS InputBatch. Baseline не публикует `Odometry` без пригодной ковариации. Описанный ниже первоначальный контракт сохраняется как проектная основа.

Это проект интерфейсов для первого совместного согласования. После короткого разбора команда фиксирует v0.1 и начинает разработку на одинаковых примерах. Изменение имени, единицы или смысла поля требует обновления схемы и потребителей в одном согласованном изменении.

## 1. Общие правила

- SI: расстояние — м, скорость — м/с, ускорение — м/с², угол — рад.
- `stamp_ns` — время события в наносекундах выбранного ROS-clock. В JSON передаем десятичной строкой: JavaScript не представляет все 64-битные целые точно.
- `run_id` отличает запуски, `seq` — порядковый номер внутри потока. Дубликаты не влияют на состояние повторно.
- Для replay все входы одного запуска используют одну шкалу времени. Для задержки исполнения отдельно используем монотонные часы процесса; их не смешиваем с `/clock`.
- Пропуск отличается от нуля. JSON использует `null` для отсутствующей численной оценки; `NaN`/`Infinity` в JSON запрещены.
- Эталонная скорость, погода и искусственная метка отказа доступны испытательному стенду, но не алгоритму. Аппаратный флаг неисправности можно передавать, только если он реально доступен во входах задачи.

## 2. Входы ядра

| Структура | Поля | Правило |
|---|---|---|
| `ControlSample` | `stamp_ns: int`, `seq: int`, `u: float`, `valid: bool` | `u ∈ [-1,1]`, кодировку задает адаптер |
| `WheelSample` | `stamp_ns: int`, `seq: int`, `wheel_id: str`, `speed_mps: float`, `valid: bool` | Один отсчет одного физического канала |
| `InitialState` | `stamp_ns`, `s_m`, `v_mps`, `covariance_4x4` | Допустимый источник начальной привязки указан в конфигурации |

Адаптер преобразует `rad/s` в `m/s` через радиус колеса; RPM сначала переводит в `rad/s`. Если исходные данные уже в `m/s`, повторно на радиус не умножаем. При неизвестном радиусе или неоднозначных единицах вход считается некалиброванным.

Нормализованная `valid` отражает проверку формата, свежести и реальных аппаратных флагов. Она не кодирует скрытое знание симулятора о буксовании.

## 3. API Python-ядра

```python
class OdometryEstimator:
    def initialize(self, initial: InitialState, config: EstimatorConfig) -> None: ...
    def ingest_control(self, sample: ControlSample) -> None: ...
    def ingest_wheel(self, sample: WheelSample) -> None: ...
    def advance_to(self, stamp_ns: int) -> Estimate: ...
    def reset(self) -> None: ...
```

`ingest_*` помещают проверенные события в ограниченную очередь. `advance_to(t)` обрабатывает новые события до `t` по времени: прогноз до события, применение ручки или колесного обновления, затем прогноз до `t`. Отсчет колеса применяется один раз. Для одинакового времени порядок фиксирован: ручка, колеса по `wheel_id`, публикация.

События старше уже рассчитанного времени отбрасываются с причиной `OUT_OF_ORDER`. Переполнение очереди явно диагностируется. Нода и CLI вызывают один и тот же API; в ядре нет файловой записи, логирования каждого тика, HTTP или импорта ROS.

`Estimate` содержит:

```text
stamp_ns, seq
s_m, v_mps, a_mps2, disturbance_mps2
covariance_4x4                 # порядок [s, v, a_act, d], row-major
sigma_s_m, sigma_v_mps
mode, valid, reason_codes[]
control_age_s, wheel_age_s     # null, если измерений еще не было
model_only_duration_s
accepted_wheel_count, rejected_wheel_count
model_version
```

`a_mps2` — полное прогнозное ускорение `dv/dt`, оно отличается от состояния `a_act`. `sigma_s_m` и `sigma_v_mps` выводятся из ковариации, а не настраиваются независимо.

При `INITIALIZING` доступен статус без численной оценки. При `INVALID` конечный последний прогноз можно передавать для диагностики с `valid=false`; если его нет или он численно поврежден, поля оценки — `null`. Потребитель сначала проверяет `valid` и `mode`.

## 4. Топики ROS 2

| Топик | Тип | Назначение |
|---|---|---|
| `/tram/control` | `odometry_msgs/msg/ControlSample` | `Header`, `seq`, `u`, `valid` |
| `/tram/wheel_speed` | `odometry_msgs/msg/WheelSample` | `Header`, `seq`, `wheel_id`, `speed_mps`, `valid` |
| `/odometry/estimate` | `odometry_msgs/msg/LongitudinalEstimate` | Канонический продольный результат и качество |
| `/odometry/filtered` | `nav_msgs/msg/Odometry` | Совместимая численная проекция результата |
| `/odometry/diagnostics` | `diagnostic_msgs/msg/DiagnosticArray` | Timeout, режим, отброшенные входы, длительность расчета |
| `/clock` | `rosgraph_msgs/msg/Clock` | Только для запуска с симуляционным временем |

В собственном ROS-сообщении вместо JSON `null` используются `has_estimate: bool`, `valid: bool` и отдельные признаки наличия возрастов входов. При `has_estimate=false` численные поля технически равны нулю, но не являются оценкой; это правило покрывается контрактным тестом. Режим — фиксированные enum-константы, причины — массив кодов.

`LongitudinalEstimate` публикуется каждый тик, включая `INITIALIZING` и `INVALID`. `nav_msgs/Odometry` публикуем только при наличии действительной конечной оценки, поскольку у этого сообщения нет собственного поля `valid`. Поэтому прекращение его потока сопровождается явным статусом; потребитель также обязан иметь timeout. «Непрерывность» не означает генерацию фиктивной достоверной позиции при потере всех входов.

### Системы координат MVP

Для условного прямого пути: `header.frame_id = "odom_1d"`, `child_frame_id = "tram_1d"`, `pose.position.x = s`, `twist.linear.x = v`, quaternion — единичный. Остальные координаты — условные значения одномерного представления. Эти frame не выдаем за реальную ориентацию трамвая на кривом участке.

`pose.covariance[0] = P_ss`, `twist.covariance[0] = P_vv`. Для неоцениваемых степеней свободы задаем большие конечные диагональные дисперсии по конфигурации, а не нули. Полная совместная ковариация `s` и `v` остается в собственном сообщении: `Odometry` не хранит все такие связи.

По определению ROS-сообщения pose относится к `header.frame_id`, а twist — к `child_frame_id`. [Исходник Odometry.msg, ветка Humble](https://raw.githubusercontent.com/ros2/common_interfaces/humble/nav_msgs/msg/Odometry.msg).

При появлении разрешенной карты маршрута отдельный компонент преобразует `s` в координаты и ориентацию по касательной, с преобразованием ковариации. Не публикуем конкурирующий TF для уже существующих `odom`/`base_link`.

## 5. Телеметрия Python → .NET → Vue

MVP: bridge отправляет HTTP-батчи на `POST /api/runs/{run_id}/telemetry`; backend раздает обновления через SignalR `/hubs/telemetry`, событие `telemetryBatch`. Частота графиков — до 10 Гц, сообщения содержат временные метки исходной оценки. Это не поток для расчета метрик: метрики используют полную частоту.

Один пример кадра:

```json
{
  "schema_version": "0.1",
  "run_id": "demo-001",
  "seq": 125,
  "stamp_ns": "2500000000",
  "s_m": 7.4,
  "v_mps": 5.1,
  "sigma_s_m": 0.8,
  "sigma_v_mps": 0.3,
  "wheel_speed_mps": 8.0,
  "control_u": 0.5,
  "mode": "MODEL_ONLY",
  "valid": true,
  "reason_codes": ["WHEEL_INCONSISTENT"],
  "model_only_duration_s": 0.4,
  "compute_ms": 0.7,
  "model_version": "physics-v1"
}
```

Значения иллюстративны. Для неопределенной скорости колеса `wheel_speed_mps=null`. Стенд может отдельно присоединить эталон по времени для графика; bridge и ядро его не вычисляют и не используют.

Backend:

| Интерфейс | Результат |
|---|---|
| `POST /api/runs` | Регистрация метаданных готовящегося запуска |
| `GET /api/runs` | Каталог запусков |
| `GET /api/runs/{id}` | Конфигурация и состояние запуска |
| `POST /api/runs/{id}/telemetry` | Прием батча; дедупликация по `(run_id, seq)` |
| `PUT /api/runs/{id}/report` | Сохранение рассчитанного Python-отчета |
| `GET /api/runs/{id}/report` | Метрики для отображения и сравнения |
| `GET /api/health` | Готовность стенда |

Начальный backend показывает запущенные из CLI эксперименты. Удаленный запуск ROS-процессов из UI добавляем только после MVP, с фиксированным каталогом сценариев и параметров.

Размер батча и очереди ограничены. При недоступном API bridge отбрасывает старую телеметрию и считает потери. Наблюдатель продолжает работу. На UI потеря связи отображается отдельно от `INVALID` модели.

## 6. Артефакты и воспроизводимость

`model.json`: `schema_version`, `model_version`, `state_order`, единицы, параметры физической модели, ограничения, настройки `Q/R`, пороги качества, область калибровки, идентификаторы обучающих поездок. Загрузка проверяет совместимость схемы и диапазоны. Начальное состояние и seed относятся к конфигурации запуска, а не к обученной модели.

`run.json`: `run_id`, `scenario_id`, `seed`, версия/хеш модели, хеш данных, commit кода, режим времени, параметры отказов, начальное состояние, характеристики машины.

`report.json`: метрики по алгоритму и сценарию, число отсчетов, единицы, интервалы пропусков, ошибка на всем доступном прогнозе и на `valid`-участках, доля валидного времени, задержки. Для отсутствующего эталона метрика — `null` с причиной, а не ноль.

Фикстуры v0.1: нормальный разгон, подозрительные колеса, `INITIALIZING`, `INVALID`, потеря связи со стендом и готовый отчет сравнения. Они позволяют DS, ROS, backend и frontend работать независимо до первого сквозного запуска.
