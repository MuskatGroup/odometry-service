# Первые ТЗ участникам команды

Эти задания можно раздать как первые карточки. Плановые оценки — ориентир объема, не обещание длительности. Подготовку, которую разрешено включать в конкурсную работу до открытия, уточняем у организаторов. Общие договоренности — [контракт v0.1](03-contracts.md), источник данных — [план стенда](09-start-data-and-testbench.md).

В рамках этих документов код не создавался. Предлагаемые CLI-команды и имена артефактов ниже — требования к будущей реализации.

## Общий старт: один созвон на 30–45 минут

Результат созвона:

- роли и владельцы каталогов подтверждены;
- единицы — SI, исходные форматы переводятся в адаптере;
- ручка в MVP: положительное значение — тяга, отрицательное — торможение, движение вперед;
- время передается по контракту, в JSON `stamp_ns` — строка;
- входы, эталон и диагностические метки симулятора разделены;
- каждая задача имеет локальную фикстуру и не ожидает готовности всего проекта.

Архитектор фиксирует общие схемы; автоматизатор — канонические тестовые последовательности; frontend и backend могут сразу использовать пример телеметрии из контракта. Модели и графики на этом этапе помечаются как синтетические.

## START-1. Автоматизатор Python: источник данных и первый evaluator

**Цель:** все участники получают один воспроизводимый пример движения и отказа без реальных датчиков.

**Зона:** `python/odometry_lab/`, `tests/fixtures/`. Первая итерация — примерно один рабочий день; базовый пример нужен раньше остальных сценариев.

**Сделать:**

1. Генератор одномерного движения с профилем ручки: разгон, выбег, торможение. Конфигурация содержит длительность, шаг времени, начальное состояние, параметры и seed.
2. Выход `events.jsonl` с `ControlSample`/`WheelSample`; `truth.jsonl` с известными скоростью и путем; отдельная конфигурация запуска. В файле событий допустимо поле-дискриминатор `kind=control|wheel`, не меняющее полезную нагрузку контракта.
3. Четыре начальных варианта: чистые данные, завышение колесной скорости, занижение вплоть до нуля и пропуск сообщений.
4. Небольшой evaluator: RMSE скорости, ошибка приращения пути на отказе, конечная ошибка пути, доля отсутствующих/недействительных оценок.
5. Команда запуска генерации и расчета метрик с описанными аргументами. На первом этапе evaluator можно проверить на вручную заданном прогнозе.

**Приемка:** один seed воспроизводится; искажение колес не меняет файл истины в тестах первого уровня; dropout означает отсутствие сообщения, а не нулевую скорость; у источника ядра нет доступа к truth; на искусственно точном прогнозе ошибка равна нулю с учетом численной погрешности.

**Следующая итерация:** зависание, общая ошибка колес, изменение действующей тяги при плохом сцеплении, рассинхронизация. Разделение двух уровней физики описано в плане стенда.

## START-2. Data scientist: первое ядро и базовые алгоритмы

**Цель:** получить численную точку сравнения до добавления адаптации.

**Зона:** `python/odometry_core/` и его unit-тесты. Первая итерация — примерно один рабочий день.

**Сделать:**

1. Реализовать API `initialize`, `ingest_control`, `ingest_wheel`, `advance_to`, `reset` из контракта.
2. Режим `wheel + hold`: последняя доступная колесная скорость и интегрирование пути, с явной маркировкой устаревших данных.
3. Режим `model-only`: простая нелинейная реакция на управление, задержка и сопротивление; начальные параметры сохраняются в конфигурации.
4. Выдавать `Estimate` одинаковой структуры, с честным указанием базового режима. На этапе без вероятностного наблюдателя неопределенность пометить как некалиброванную в диагностике; не выдавать нулевую дисперсию за точное знание.
5. Проверить ядро на собственной крошечной последовательности, затем на общем генераторе.

**Приемка:** ядро импортируется без ROS; повторяемый вход дает тот же выход; старое колесное измерение не применяется повторно как новое; на постоянных 10 м/с за 5 секунд при согласованных начальных условиях приращение пути равно 50 м; все входные единицы и начальная привязка документированы.

**После первого общего отчета:** EKF, управление доверием, затем адаптация возмущения. Порогам и параметрам до получения реальных данных присваивается статус экспериментальных.

## START-3. Архитектор: ROS-каркас и единое окружение

**Цель:** второй участник команды может поднять ноду и получить результат из тестовых входов.

**Зона:** `ros2_ws/`, `infra/`, `contracts/`. Первое ограничение по времени — поднять минимальную цепочку за 4–8 часов; незнакомые особенности ROS могут потребовать дополнительного времени.

**Сделать:**

1. Зафиксировать проверяемую среду Ubuntu 22.04 + ROS 2 Humble и инструкцию запуска. Windows-разработчикам дать воспроизводимый Linux-вариант; численное ядро и web продолжают разрабатываться отдельно.
2. Создать пакет сообщений и ноду, которая принимает ручку/колеса и вызывает stub того же API, что реализует DS.
3. Сделать тестовый издатель: сначала простые константы, затем чтение общего файла событий. Он только воспроизводит события, а не реализует вторую физику симулятора.
4. Публиковать продольный результат и статус; обеспечить один источник времени и режим воспроизведения.
5. Добавить launch и smoke-тест получения сообщений. После появления ядра заменить stub без изменения потребителей.

**Приемка:** другой участник выполняет инструкцию; вход и выход видны в ROS; тайм-аут и пауза времени не выглядят штатным движением; отключение web не меняет расчет; в репозитории описано, какие части пока заглушки.

**Следующая итерация:** telemetry bridge, измерения задержек, реальные типы сообщений организаторов. Настройку CPU и переход на C++ решаем после уточнения требований.

## START-4. Full-stack A: backend на контрактных примерах

**Цель:** дать frontend готовые endpoints, а Python-разработчикам — приемник телеметрии и отчета.

**Зона:** `apps/api/`. Первая итерация — 4–8 часов.

**Сделать:**

1. `POST/GET /api/runs`, получение одного запуска, прием батчей телеметрии и сохранение/выдачу отчета по контракту.
2. SignalR-событие `telemetryBatch` и демонстрационный источник кадров из фикстуры.
3. Проверку схемы, сохранение `stamp_ns` без потери точности, дедупликацию по `(run_id, seq)`.
4. Ограничение размеров батча и очереди; простое файловое хранение либо SQLite в рамках выбранного стека.
5. Краткое описание endpoints и пример вызова для Python bridge.

**Приемка:** frontend получает один фиктивный запуск и отчет; одинаковый батч не удваивает данные; сервер принимает `null` в предусмотренных полях; вычисление научных метрик остается в Python.

**Следующая итерация:** подключение bridge и реальных отчетов. Управление ROS-процессами из UI и сложный каталог экспериментов пока не входят в задачу.

## START-5. Full-stack B: экран разбора одного эксперимента

**Цель:** команда видит связь ручки, колесных ошибок и результата оценивания.

**Зона:** `apps/web/`. Первая итерация — 4–8 часов.

**Сделать:**

1. Экран одного запуска с общей временной осью: ручка, колесная скорость, оцененная скорость, эталон при его наличии, путь/ошибка и режим качества.
2. Локальный провайдер фикстур через тот же интерфейс данных, который затем использует backend.
3. Отображение инициализации, недействительной оценки, отсутствующего эталона и потери соединения.
4. Чтение готовых метрик из отчета; временную ось строить из относительной разности timestamp без потери точности.
5. Подключение к API после его готовности. UI показывает пометку «синтетический сценарий» для тестового источника.

**Приемка:** на графике можно найти интервал отказа; нулевая колесная скорость отличается от отсутствующего измерения; недоступный эталон не рисуется как нулевой; разрыв связи не оставляет впечатление свежих данных; большие timestamp не искажают ось времени.

**Следующая итерация:** сравнение baseline и наблюдателя, полоса неопределенности только при наличии осмысленной оценки. Карта маршрута не нужна для первого эксперимента.

## Результат первого объединения

На одном общем сценарии должны работать:

1. Генерация входов и отдельного эталона.
2. Запуск baseline в Python и сохранение оценок.
3. Расчет численной ошибки.
4. Воспроизведение тех же событий через ROS и получение выходных сообщений.
5. Просмотр запуска и отчета на web-стенде, сначала допускается импорт файлов.

Сначала закрываем пункты 1–3: это минимальная исследовательская цепочка. Пункты 4–5 развиваются параллельно. После этого каждая новая версия алгоритма оценивается одним и тем же способом, а реальные данные подключаются через адаптер.
