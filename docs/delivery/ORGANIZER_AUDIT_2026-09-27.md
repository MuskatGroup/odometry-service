Player прочитал весь bag и завершился с кодом 0, нода самостоятельно не завершалась.
Однако последние записанные оценки отстают от конца исходного bag примерно на 78 с
на оси simulated time. Поэтому «player завершился» здесь **не означает**, что runtime
обработал весь прогон своевременно. Это отрицательный результат проверки непрерывности
под нагрузкой 5×, а не успешная финальная демонстрация.

В записи все 16 530 оценок содержат ускорение; скорости, позиции, ускорения и элементы
ковариации конечны. Одна оценка имеет `has_map_pose=True` при `valid=False`.
Ускорение не сравнивалось с независимым эталоном.

Проценты `valid` выше относятся к полученным сообщениям, а не ко всему времени bag.
Checker не оценивает отсутствующий выход. Сравнение ошибок двух длинных прогонов
не является чистым A/B: разные начальные условия, интервалы и нагрузка recorder.

## Выявленные проблемы

1. **Команды запуска с числовым `vehicle_id` падают.** В ноде параметр объявлен строкой,
   но ROS разбирает `vehicle_id:=30618` как integer. Это воспроизведено: процесс завершился
   с `InvalidParameterTypeException`, ни одного выхода. Рабочий Bash-вариант:
   `-p "vehicle_id:='30618'"`; в YAML — `vehicle_id: "30618"`.
   В launch следует явно задавать `ParameterValue(..., value_type=str)` и проверить запуск.

2. **Общая команда pytest сломана вложенным пакетом организаторов.** Разделить коллекцию
   обычных Python-тестов и ROS-checker. Сейчас workaround:
   `python -m pytest tests --ignore=tests/check-code -q`.

3. **ROS-регрессия на задержанных колёсах не зелёная.**
   `tests/integration/test_ros.py:177` создаёт timestamp `now - 80ms` сразу после
   инициализации. Он может оказаться раньше начала истории фильтра, которую fixed-lag
   не восстанавливает. Нужно сделать время сценария детерминированным и отдельно
   проверять начальный буфер и задержки после прогрева. По одному падению нельзя заключать,
   что реальный поток всё ещё массово теряет колёса: short bag run показал 0 поздних отказов.

4. **`input_to_publication_ms` не является end-to-end задержкой входа.**
   `runtime.py` вычитает время начала текущего tick из ROS-времени при публикации.
   На коротком bag прогоне эта метрика и все её процентили равны нулю. Нельзя предъявлять
   их как доказательство p99 ≤100 мс. Нужны раздельные метрики времени приёма, очереди,
   расчёта, публикации и возраста использованных измерений на монотонных часах.

5. **Порядок обновлений одного timestamp расходится с описанием.**
   `_process_group` собирает wheel candidates, но применяет GNSS corrections внутри цикла,
   а итоговый wheel update делает после цикла. Поэтому фактически GNSS может обновиться
   раньше колёс, хотя документирован порядок wheels → GNSS velocity → GNSS position.
   Диагностический запуск с четырьмя событиями одного timestamp подтвердил порядок
   `LongitudinalVelocityCorrection → AlongTrackPositionCorrection → wheel`.
   Для `disabled` это не влияет, для intermittent нужен отдельный regression test.

6. **Семантика недействительной позиции требует решения.**
   `_publish` публикует `/result/position` при наличии геометрии и covariance даже при
   `result.valid=False`. В `Odometry` нет собственного флага valid, checker считает такой
   результат обычной оценкой. Следует явно согласовать политику выдачи и документацию;
   отсутствие результата checker отдельно не штрафует, поэтому также нужна coverage.

7. **Полная позиция вне карты не поддерживается.** Нельзя подменять начальную привязку
   первой точкой JSON для bag, который начинается в другом месте. Нужны предоставленные
   начальные условия/дополнительная карта либо явное ограничение области проверки.

8. **Failure Lab и runtime используют разную модель одного YAML.**
   `odometry_lab.calibrate.config_from_profile` загружает шумы, wheel health, лаг и
   сопротивление, но не загружает traction/braking maps и не включает адаптацию `d`.
   Проверено на `30618.yaml`: runtime имеет обе таблицы и `adapt_disturbance=True`,
   Lab — обе таблицы `None`, `adapt_disturbance=False`. Поэтому старые результаты M1-cal
   не являются проверкой production-модели. Нужен общий загрузчик и повторный benchmark.

9. **Длинная пауза в вычислительном цикле при нагрузке.** В полном intermittent 5×
   зарегистрирован шаг 11,03 с при малом p99 1,31 мс; к концу bag выход отстал примерно
   на 78 simulated секунд. Нужно профилировать длинный прогон, очереди и обработку
   выхода за карту. Точная причина паузы этим аудитом не установлена. Нельзя считать
   ограничение peak ≤250 мс подтверждённым по одному хорошему p99.

10. **Нечистое завершение по SIGINT.** После штатной остановки runner в логах есть
    `rcl_shutdown already called` и exit code 1; в полном intermittent также попытка
    публикации после инвалидирования context. Это отдельный дефект shutdown, а не
    самостоятельное падение в середине bag. Требуются корректная обработка SIGINT,
    остановка executor и проверка состояния context перед shutdown.

## Воспроизведение

В корне проекта, PowerShell (Docker Desktop должен работать):

```powershell
docker build -f infra/Dockerfile.ros -t odometry-audit:local .
docker run -d --name odometry-audit --cpus 2 `
  --mount "type=bind,source=$((Get-Location).Path),target=/repo" `
  odometry-audit:local sleep infinity
docker exec -it odometry-audit bash
```

В контейнере:

```bash
source /opt/ros/humble/setup.bash
source /workspace/ros2_ws/install/setup.bash
mkdir -p /checker_ws/src
cp -r /repo/tests/check-code/src/checker_ros /checker_ws/src/
cd /checker_ws
colcon build
source install/setup.bash
export ROS_DOMAIN_ID=87

# Новое имя для каждого запуска: runner сохраняет summary, logs и results rosbag.
python3 /repo/tools/run_organizer_audit.py \
  --name strict-repeat --offset 230 --duration 60 --rate 1

# Полный оставшийся участок при штатной скорости — около 18 минут.
python3 /repo/tools/run_organizer_audit.py \
  --name strict-full-realtime --offset 230 --duration 0 --rate 1

# Дополнительный режим с GNSS. Это НЕ проверка «GNSS только как эталон».
python3 /repo/tools/run_organizer_audit.py \
  --name intermittent-repeat --policy intermittent --offset 0 --duration 0 --rate 1
```

Runner использует официальный `MetricsNode`, запускает production executable и player
отдельными процессами, сохраняет их логи и снимает диагностические показатели.
При `disabled` он явно получает **только начальные условия** из первой эталонной точки
выбранного фрагмента. Для независимого финального зачёта эти условия должны быть
предоставлены извне по правилам организаторов.

Результаты лежат в `artifacts/organizer-audit/<name>/summary.json`, `runtime.log`,
`player.log`, `recorder.log`, `results/`. В первых прогонах аудита запись results ещё
не была включена; их доказательства — JSON и логи. В полном intermittent-прогоне
запись выходов включена.

После завершения проверки:

```powershell
docker stop odometry-audit
```
