# Проверка исправленного runtime — 27.09.2026

Ветка `fix/runtime-validation`, база `origin/main` (`a7a22af`). Это отдельная итерация;
старые таблицы в `VALIDATION.md` оставлены как история, а не как результат текущей ROS-ноды.
Исходные model YAML не переобучались и не подбирались по test-выборке.

Следующая итерация алгоритма и парные метрики до/после —
[FREEZE_VALIDATION.md](FREEZE_VALIDATION.md). Таблицы ниже относятся к runtime до

## Что исправлено

- Один строгий загрузчик YAML для ROS и лаборатории: тяга, торможение, сопротивление,
  шумы, wheel health, ограничение и адаптация возмущения больше не расходятся.
- Лабораторный EKF получает уклон из карты по **своей** оценке позиции. Окна не пересекают
  смену маршрута. s0/v0 для окон явно считаются заданными начальными условиями по GNSS.
- `calibrate-noise` использует полный профиль и identification-записи соответствующего
  трамвая, а не переносит один результат от встроенной модели во все YAML.
- `colcon build` устанавливает runtime-библиотеки и assets через `odometry_python`.
  Launch корректно типизирует числовой `vehicle_id` как строку, поддерживает sim time,
  автоматически находит карту и профили в install/share.
- Запуск на движении не предполагает нулевую скорость: при `initial_v_mps=-1` стартовая
  скорость берётся из первой пригодной группы колёс. Затем действует обычный gating.
- Первая GNSS-привязка не стирает очередь, управление, скорость и адаптированную динамику.
  Поздние события не перематывают фильтр назад. Начальное GNSS-окно ограничено 5 секундами.
- Исправлена воспроизведённая гонка `InvalidHandle` при закрытии GNSS в Humble:
  callbacks после закрытия игнорируются, объекты подписок живут до остановки ноды.
- Без карты публикуется относительный путь (`odom`), за её концом — along-track координата
  (`track/<route>`). Это не выдаётся за XY-карту; скорость не инвалидируется из-за одной
  только недоступности карты.
- Задержка callback→публикация измеряется steady clock отдельно от времени вычисления.
  Сетевую/DDS-задержку до вызова callback этот показатель не измеряет.

## Offline benchmark на реальных данных

13 недублирующихся test-записей, по 120 секунд; 8 сценариев × 2 модели = 208 прогонов.
Профиль `configs/models/default.yaml`, начальные s0/v0 заданы по GNSS, дальнейшие
GNSS-коррекции запрещены (`never`). Отказ длится 20 секунд, с 50-й секунды окна.
Ниже **среднее RMSE по записям**, а не RMSE единой конкатенированной траектории.

| Сценарий | Колесный baseline, м/с | Исправленный EKF, м/с | EKF, RMSE пути, м |
|---|---:|---:|---:|
| Чистые данные | 0,075 | 0,063 | 1,56 |
| Пропало одно колесо | 0,075 | 0,063 | 1,56 |
| Залипло одно колесо | 0,774 | 0,065 | 1,55 |
| Выбросы одного колеса | 0,559 | 0,063 | 1,56 |
| Проскальзывание одного колеса | 0,869 | 0,099 | 2,28 |
| Заблокировано одно колесо | 1,703 | 0,063 | 1,56 |

| Залипли оба колеса | 1,517 | 1,461 | 43,33 |

При потере обоих колёс валидность — 90,9%: после 10 секунд без достоверной одометрии
фильтр честно помечает прогноз невалидным. Ошибки в таблице включают и эти участки.
При совместном залипании валидность 97,5%, но точность плохая: флаг valid не гарантирует
отсутствия скрытого общего отказа. Это существенное ограничение.


Полные локальные результаты: `artifacts/runtime-validation/lab-test/real-benchmark.{json,md}`.

## ROS-прогоны

Автоматизация: `tools/validate_rosbag.py`; команды и состав артефактов — [RUN.md](RUN.md).
Контейнер ограничен 2 CPU и 512 МБ, включая ноду, проигрыватель и сборщик результатов.
Сайт/API в измерении не участвуют. Относительные координаты никогда не сравниваются с XY
эталона как будто они находятся в frame `map`.

## Что остаётся улучшить

1. Общий отказ двух колёс: независимый диагностический прогноз и проверка гипотез
   проскальзывания/остановки на identification/validation, без настройки по опубликованному test.
2. Инициализация вне Pathgraph: без направления/карты абсолютная XY-позиция не наблюдаема
   по трём входам. Нужны явно переданная начальная привязка, расширенная карта или другой сенсор.
3. Калибровка covariance, систематическая проверка холодного старта и общего slip/scale bias,
   новые маршруты и загрузки. Сейчас uncertainty — инженерная оценка, не гарантия безопасности.
4. Полный набор длительных ROS-прогонов на независимых записях и целевом компьютере,
   end-to-end задержка с меткой на стороне источника. Один компьютер и один bag недостаточны
   для заявления о готовности к эксплуатации на реальном трамвае.
