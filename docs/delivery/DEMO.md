# Демонстрация

Сайт показывает готовые запуски: он **только читает** результаты и ничего не считает.
Он не входит в боевой запуск ROS и не ограничен лимитами контейнера соревнования
(0,5 ГБ памяти, 2 ядра): там работает только нода оценки.

## 1. Что показывает сайт (схема 0.3)

| Блок | Содержание |
|---|---|
| Шапка | запись, трамвай, пресет, внесённый отказ, покрытие эталона |
| Метрики | RMSE, 95-й процентиль и смещение скорости, RMSE и итоговая ошибка пути, доля валидного времени |
| Карта | Pathgraph, эталонный трек по GNSS и оценка алгоритма в метрах MGRS 37UCB |
| Скорость | оценка, колёса, эталон, интервал 95 %, розовым окно отказа |
| Ошибка скорости | оценка минус эталон во времени |
| Режим фильтра | `FUSED`, `DEGRADED`, `MODEL_ONLY`, `INVALID` |
| Ручка и путь | позиция контроллера, пройденный путь и эталон пути |
| Внесённые отказы | тип, колёса, дрейф пути и максимальная ошибка скорости за окно |
| GNSS-коррекции | сейчас «недоступны»: ядро их пока не принимает |
| События качества | смены режима с причинами |

Метрики, которых нет, показываются как «—», а не как ноль.

## 2. Запуск на своей машине (без Docker)

Нужны Python 3.10+, .NET 10 и Node 22. Предварительно один раз построить эталон:

```bash
python dataset/analysis/build_reference_table.py
```

Терминал 1 — API (порт 8080):

```bash
ASPNETCORE_URLS=http://127.0.0.1:8080 dotnet run --project apps/api/Odometry.Api.csproj
```

Терминал 2 — сайт (порт 5173, проксирует API):

```bash
cd apps/web && npm ci && npm run dev
```

Терминал 3 — загрузить запуски на реальной записи (`--api` отправляет результат на сайт):

```bash
python -m odometry_lab.cli real-run --bag 30618_2050d396 --scenario none      --api http://127.0.0.1:8080
python -m odometry_lab.cli real-run --bag 30618_2050d396 --scenario slip-1    --api http://127.0.0.1:8080
python -m odometry_lab.cli real-run --bag 30618_2050d396 --scenario dropout-2 --api http://127.0.0.1:8080
```

Затем открыть <http://127.0.0.1:5173>. Сценарии: `none`, `freeze-1`, `freeze-2`, `dropout-1`,
`dropout-2`, `spike-1`, `slip-1`, `lock-1`. Пресеты: `B0`, `B1`, `B2`, `M1`, `M2`, `M1-cal`
(по умолчанию `M1-cal` с калиброванными шумами из `configs/models/default.yaml`).
Окно по умолчанию 120 с, отказ на 50-й секунде длиной 20 с (`--window`, `--fault-start`,
`--fault-len`).

## 3. Запуск в Docker

```bash
docker compose up --build console      # сайт и API на http://localhost:8080
```

Затем загрузить запуски командами из раздела 2 с `--api http://localhost:8080`.
Синтетическая демонстрация без данных организаторов: `docker compose --profile demo up --build`.

## 4. Сценарий показа

1. **Нормальное движение.** Запуск `none`: оценка совпадает с эталоном на карте и на графике
   скорости; режим `FUSED`; ошибка скорости около 0,05–0,1 м/с.
2. **Проскальзывание одного колеса.** Запуск `slip-1`: колесо `front` на 20 секунд завышает
   скорость в 1,5 раза; в окне отказа видно расхождение колёс, оценка почти не сдвигается.
3. **Оба колеса пропали.** Запуск `dropout-2`: режим переходит в `MODEL_ONLY`, интервал 95 %
   расширяется, ошибка растёт; после возвращения колёс оценка восстанавливается.
4. **GNSS.** Эталонный трек виден на карте всегда, но алгоритм GNSS во время работы не
   использует. Коррекции по GNSS появятся после подключения ядра (блок «GNSS-коррекции»).
5. **Итог.** Сравнить метрики трёх запусков и сопоставить с таблицей в
   [VALIDATION.md](VALIDATION.md).

## 5. Ограничения

- Показаны запуски на выбранных вручную окнах реальных записей, а не весь набор.
- Живой режим (WebSocket/SignalR) остался от предыдущей версии и работает с синтетическим
  источником.
- Ковариация EKF показывается, но не калибрована.
- Сайт не проверялся на ширине меньше 800 пикселей.
