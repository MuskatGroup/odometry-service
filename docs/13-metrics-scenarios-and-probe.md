# Метрики, сценарии отказов, бенчмарк и probe

Дополняет [docs/11](11-adapters-and-integration.md) и [docs/12](12-core-ekf-and-ros-node.md). Реализует расчет метрик из [docs/05](05-validation-and-demo.md), сценарии из [docs/09](09-start-data-and-testbench.md) и генерацию черновика профиля для неизвестных данных. Проектные документы 01–10 не менялись.

## Что добавлено

- `metrics.py` — метрики docs/05 (CLI: `--truth` и `--faults`, блок `metrics` в `report.json`): линейная интерполяция эталона на сетку оценок, MAE/RMSE/p95/max/смещение скорости и пути, ошибка в конце, доступность и доли режимов, дрейф пути на окне отказа, ошибки через 1/5/15/30 с после потери колес, детектор (precision, recall, задержка обнаружения, время восстановления), покрытие ±1.96σ по режимам. Начало пути выравнивается один раз по первой оценке и одинаково для всех алгоритмов. Кадры без оценки и вне диапазона эталона считаются отдельно, а не как нули. Прежний `accuracy` (точные совпадения timestamp) сохранен.
- `emulator.py` — список `faults` со сценариями измерений (`slip`, `scale`, `lock`, `freeze`, `dropout`) и физики (`grade`, `traction_scale`), параметры физики (`traction_gain`, `brake_gain`, `drag_mps`, `actuator_tau_s`), профиль ручки `control_profile`. Экспорт `faults.json` с окнами отказов для оценщика. Прежние конфиги дают тот же поток данных.
- `runner.py` — `report.json` содержит `compute_ms` (p50/p95/p99/max времени `ingest`/`advance_to` на этой машине). В `estimates.jsonl` время не пишется, поэтому replay остается побайтово одинаковым.
- `model.py` — переключатели ablation `use_wheels` (B1), `robust` (B2), `adapt_disturbance` (M1/M2), а также защиты, найденные бенчмарком (см. ниже).
- `bench.py` — `python -m odometry_io.bench --output work/bench --seeds 3`: 10 сценариев × варианты B0/B1/B2/M1/M2 × seed, таблицы `bench.md` и `bench.json`, внутренние критерии docs/05, параметры `--channels N` и `--variant train|holdout`.
- `probe.py` — `python -m odometry_io.probe data.csv --write profile.json`: черновик профиля по образцу данных.

## Бенчмарк: что показал (синтетика, медианы по seed)

Физика симулятора намеренно отличается от параметров модели по умолчанию (усиление, лаг привода, сопротивление), а параметры модели не откалиброваны. Ошибка пути в конце прогона, м (выборка `train`, 4 канала, 3 seed):

| сценарий | B0 wheel+hold | B1 model-only | B2 fixed-EKF | M1 robust (по умолчанию) | M2 robust+d |
|---|---|---|---|---|---|
| clean | 0.0 | 2.2 | 0.0 | 0.0 | 0.0 |
| slip_one (1 колесо из 4) | 0.2 | 2.2 | 0.2 | 0.0 | 0.0 |
| slip_two (2 колеса из 4) | 4.4 | 2.2 | 1.7 | 0.0 | 0.0 |
| common_slip (все колеса ×1.4, 5 с) | 7.1 | 2.2 | 7.1 | 8.5 | 9.4 |
| lock (юз, все колеса 0, 3 с) | 9.2 | 2.2 | 9.2 | 0.2 | 0.2 |
| freeze (зависание, 5 с) | 4.5 | 2.2 | 4.6 | 0.0 | 0.1 |
| dropouts (1/5/15/30 с) | 13.7 | 2.2 | 0.3 | 0.3 | 5.5 |
| grade_in_dropout | 1.7 | 168.9 | 0.1 | 0.1 | 0.3 |
| grade_in_common_slip | 12.4 | 111.1 | 12.4 | 3.0 | 0.1 |
| load_change (тяга ×0.6) | 0.1 | 110.6 | 0.0 | 0.0 | 0.0 |

Медианный дрейф пути на 30 коротких (1–5 с) отказах измерений: B0 4.3 м, M2 0.05 м; критерий docs/05 (≥20%) выполнен, как и допуск на чистых данных. Критерии ориентировочные и получены на синтетике.

### Проверка на отложенной выборке

`--variant holdout` меняет физику (другие усиления, лаг, сопротивление, шум, начальная скорость, цикл ручки), тайминги и силу отказов и использует другие seed. Сумма ошибок пути в конце по сценариям, м (5 seed): train — B0 53.3, M1 12.3, M2 15.7; holdout — B0 162.9, M1 14.2, M2 28.2. Юз, зависание, буксование одного и двух колес и пропуски обобщаются (M1 около 0–2 м против 4–85 м у B0). M2 выигрывает у M1 отдельными сценариями (`grade_in_common_slip` на train), но на отложенной выборке проигрывает (14.4 против 1.0 м) и на пропусках (2.9 против 1.1 м). Поэтому **`adapt_disturbance=false` — значение по умолчанию**. Это решение по синтетике, его нужно пересмотреть на реальных данных.

### Что осталось неисправимым или неизвестным

- **Общее буксование** (все колеса ошибаются согласованно) не обнаруживается и не исправляется: в `common_slip` M1/M2 не лучше B0 (8.5–9.4 против 7.1 м). Это предел наблюдаемости из docs/01: без независимого источника или знания состояния сцепления его не убрать. С одним каналом любое буксование колеса общее, и EKF там не лучше baseline; с двумя каналами, буксующими одновременно, то же самое.
- **Точность на реальном трамвае неизвестна.** Модель без колес (B1) уходит на 110–170 м при смене нагрузки или уклоне, а на holdout на 146 м даже без отказов: параметры ручки не откалиброваны. Калибровка `kt/kb/tau` по данным еще не реализована.
- Результат `grade_in_common_slip` сильно зависит от тайминга и не является устойчивым свойством.
- Время шага: p99 не выше 0.26 мс на `ingest`/`advance_to` (Windows, Python 3.14, без ROS). Это измерение ядра, а не гарантия реального времени; цель docs/02 (не более 2 мс) на целевом железе не проверялась.
- Покрытие ±1.96σ по скорости 0.9–1.0; проверялось только на синтетике.

### Дефекты, найденные бенчмарком и исправленные

1. **Схлопывание на блокировку колес.** При устойчивой блокировке `P_vv` росла без принятых обновлений, гейт по NIS открывался, и оценка уходила на колеса (0.05 м/с при истинных 3 м/с). Исправлено: дисперсия гейта ограничена (`gate_sigma_cap`), добавлено повторное захватывание `WHEEL_REACQUIRED` после `reacquire_s` без принятых обновлений, при `adapt_disturbance=false` состояние `d` фиксируется без роста дисперсии.
2. **Повторное захватывание портило ускорение.** Первая версия перезаписывала `v` и обнуляла кросс-ковариации, оставляя `a_act` устаревшим: после долгого пропуска ошибка пути была 10–17 м вместо около 1 м. Теперь захват — обычное полное EKF-обновление в обход гейта.
3. **Зависание датчика не обнаруживалось** (ошибка 4.5–11.7 м, детектор 0%). Добавлен детектор `WHEEL_FROZEN`: канал, повторяющий одно точное значение дольше `freeze_s`, пока по ручке ожидается изменение скорости (`|a| ≥ freeze_min_accel`), исключается. Постоянные показания при выбеге зависанием не считаются. Ограничение: если реальный датчик зависает при почти постоянной скорости, или показания квантованы так, что повторы легитимны при ускорении, детектор ошибется в одну из сторон; проверять на данных.
4. **Слабый гейт по слитому значению.** Медиана из 2 каналов равна среднему, поэтому умеренное буксование одного из двух колес проходило. Добавлено голосование по каналам (`channel_gate`): каналы, не согласные с прогнозом модели, исключаются, если хотя бы один канал согласен. Если не согласен никто, решает общий гейт.

`gate_sigma_cap` после появления детектора зависания на результат не влияет (0.5, 1.0 и 2.0 дают одинаковые числа); значение 1.0 оставлено. Остальные пороги (`gate_normal=9`, `gate_reject=36`, `reacquire_s=10`, `freeze_s=1`) выбраны без перебора.

## Запуск

```powershell
$env:PYTHONPATH = "$PWD\src"
python -m odometry_io.bench --output work/bench --seeds 3
python -m odometry_io.bench --output work/holdout --seeds 5 --variant holdout --channels 2
python -m odometry_io.bench --output work/bench2 --seeds 3 --preset B0 --preset M1 --scenario lock --model-config work/model.json
python -m odometry_io.emulator --config work/scenario.json --output work/syn      # input.jsonl, truth.jsonl, faults.json
python -m odometry_io --input work/syn/input.jsonl --format jsonl --profile examples/profile-emulator.json --estimator model --truth work/syn/truth.jsonl --faults work/syn/faults.json --output work/run
```

Формат `faults` в конфиге эмулятора (шаги, конец исключен; `channels` по умолчанию все):

```json
{"faults": [{"type": "scale", "start": 400, "end": 500, "channels": [0], "amount": 1.5},
            {"type": "dropout", "start": 900, "end": 1200},
            {"type": "grade", "start": 900, "end": 1300, "amount": 0.3}]}
```

## probe: как пользоваться и чего ждать

```powershell
python -m odometry_io.probe data.csv --write profile.json    # либо .jsonl, вложенные объекты и массивы поддерживаются
```

Скрипт находит колонку времени и угадывает единицу (по имени поля или порядку величины), счетчик `seq`, ручку (числовые ступени, значения в [-1, 1] или категории), каналы скорости и единицы (`m/s`, `km/h`, `rad/s`, `rpm`), флаги валидности, `missing=skip` для пустых значений, агрегаты, которые нельзя сливать со своими составляющими. Затем он проверяет черновик, прогнав образец через `normalize`. В stderr выводится список находок и TODO; код возврата 1, если черновик еще не нормализует образец.

Ограничения: все догадки эвристические. Радиус колеса не угадывается и должен быть задан вручную для `rad/s` и `rpm`, иначе черновик не загрузится. Значения категорий ручки (тяга +0.6, тормоз −0.4, выбег 0) — заглушки. Флаги «fault/error» (1 = плохо) не используются автоматически. Пары `sec`/`nanosec` профилем не читаются. Для ROS-топиков `probe` не запускается: типы и поля там задаются в конфигурации моста.
