# Система координат и GNSS extrinsics

Дата: 26 сентября 2026.

Этот документ фиксирует полученные от организаторов параметры, используемые для
преобразования GNSS в положение `base_link` и для публикации `/result/position`.

## 1. Подтверждённая система координат

Организаторы указали MGRS-код `37UCB035858` и пример:

```text
latitude  = 55.8088325462547
longitude = 37.4602768500852

x = 103501.6309
y =  85876.1201
z =    167.4109
```

Преобразование WGS84 → UTM zone 37N (`EPSG:32637`) для этой точки даёт:

```text
easting  =  403501.6309
northing = 6185876.1201
```

Следовательно, подтверждённая формула XY:

```text
x = UTM easting  - 300000
y = UTM northing - 6100000
```

Пример совпадает с ответом организаторов до `0,0001 м`.

Используется фиксированный опорный квадрат `37UCB`. При физическом переходе в соседний
квадрат `37UDB` координата `x` **не сбрасывается** по modulo `100000`, а непрерывно
становится больше `100000`. Для примера `easting=403501.6309` получается
`x=103501.6309`, а не `3501.6309`.

В коде это должно быть именованной конфигурацией:

```yaml
projection:
  crs: EPSG:32637
  mgrs_reference_grid: 37UCB
  false_easting_m: 300000.0
  false_northing_m: 6100000.0
  continuous_across_100km_cells: true
```

Применять `% 100000` запрещено.

## 2. `base_link` и тележки

Подтверждено:

- начало `base_link` — вертикальная ось поворота передней тележки;
- высота начала — точка контакта колеса и рельса;
- `x` направлена вперёд, `y` влево, `z` вверх;
- задняя тележка находится на расстоянии `7.55 м` от передней.

В системе `base_link`:

```text
front_bogie_pivot = [ 0.00, 0.0, 0.0]
rear_bogie_pivot  = [-7.55, 0.0, 0.0]
```

Это расстояние нужно для определения ориентации кузова на кривой. Ориентация кузова
не обязана в точности совпадать с касательной Pathgraph в точке передней тележки:
тележки поворачиваются относительно кузова. При отсутствии GNSS приближённый yaw кузова
следует вычислять по хорде между положениями передней и задней тележек на пути.

## 3. TF GNSS-антенн

Организаторы предоставили положения антенн в `base_link`:

```text
base_link → master = [-9.873, 0.0, 3.0] м
base_link → rover  = [ 2.563, 0.0, 3.0] м
```

Расстояние между антеннами по продольной оси:

```text
baseline = 2.563 - (-9.873) = 12.436 м
```

Master расположен на `2.323 м` позади оси задней тележки, rover — на `2.563 м`
впереди оси передней тележки. Оба приёмника находятся на высоте `3 м` над `base_link`.

## 4. Преобразование одной антенны в `base_link`

Пусть `t_base_antenna` — предоставленный TF, а `R_map_base(yaw)` — поворот кузова.
Тогда:

```text
p_map_base = p_map_antenna - R_map_base * t_base_antenna
```

Для master:

```text
p_base = p_master - R(yaw) * [-9.873, 0, 3]
```

Для rover:

```text
p_base = p_rover - R(yaw) * [2.563, 0, 3]
```

Для точного XY нужен yaw кузова, а не только касательная пути.

## 5. Использование двух антенн

Если fixes синхронизированы, направление от master к rover совпадает с положительным
направлением `x` кузова:

```text
yaw_body = atan2(y_rover - y_master, x_rover - x_master)
```

Положение `base_link` в XY можно получить непосредственно интерполяцией по baseline:

```text
alpha = 9.873 / 12.436 = 0.793904793
p_base_xy = p_master_xy + alpha * (p_rover_xy - p_master_xy)
```

Эквивалентный контроль — независимо преобразовать обе антенны через их TF и сравнить
две оценки `base_link`. Их разность является сильной диагностикой GNSS/синхронизации.

Требования к реализации:

1. Синхронизировать master и rover по `header.stamp` с ограниченным tolerance.
2. Не усреднять несинхронные fixes без интерполяции.
3. Проверять длину измеренного baseline относительно `12.436 м`.
4. Отклонять yaw при слишком коротком/искажённом baseline или плохом GNSS status.
5. При доступности только одной антенны брать yaw из предыдущего dual-fix результата
   либо из геометрии Pathgraph и увеличивать covariance.
6. После преобразования `base_link` проецировать именно его, а не антенну, на Pathgraph.

## 6. Высота

Организаторы подтвердили, что `/result/position` содержит положение `base_link`. Поэтому
геометрически:

```text
z_base = z_antenna - 3.0 м
```

Организаторы дополнительно сослались на REP-103. Он задаёт метры, правую систему и
ориентацию `z` вверх, но не определяет однозначно vertical datum конкретного датасета.
Ответ всё ещё не уточняет явно, является ли выходной `z` эллипсоидальной высотой
`NavSatFix.altitude` без геоидной поправки. До дополнительного подтверждения:

- не выполнять скрытое преобразование геоида;
- хранить vertical datum в конфигурации;
- проверить на реальном сообщении, что `NavSatFix.altitude - 3.0` совпадает с выданным
  примером `z=167.4109`;
- отдельно логировать источник и применённый vertical offset.

Официальный текст REP-103:
<https://github.com/openrobotics/reps/blob/main/_posts/rep-0103.md>.

## 7. Влияние на Pathgraph и runtime

### Инициализация от GNSS

```text
master/rover WGS84
  → fixed-CB continuous XY
  → antenna TF compensation
  → base_link XYZ/yaw
  → projection to directed Pathgraph
  → route_id, s0, cross-track
```

### Периодическая коррекция

Каждый последующий валидный fix сначала переводится в `base_link`, и только затем
создаёт along-track correction. Нельзя корректировать состояние координатой антенны:
ошибка будет зависеть от yaw и достигать `9.873 м` для master.

### Работа без GNSS

В `route_start`:

- `base_link` начинается в первой точке направленного Pathgraph;
- позиция передней тележки равна `pose_at(s)`;
- положение задней тележки ищется на том же пути с расстоянием между pivot около
  `7.55 м`;
- yaw кузова берётся по хорде `rear_pivot → front_pivot`;
- антенны для расчёта runtime pose не нужны, но их TF используется в offline truth.

## 8. Тесты

1. Контрольный lat/lon преобразуется в `x=103501.6309`, `y=85876.1201`.
2. Точка восточнее `easting=400000` сохраняет `x>100000`, без modulo-скачка.
3. Синтетический yaw `0`, `pi/2`, `pi` правильно компенсирует TF обеих антенн.
4. Две идеальные антенны дают одинаковый `base_link`.
5. Измеренный dual-antenna baseline проверяется против `12.436 м`.
6. Rear bogie находится в `[-7.55,0,0]` относительно `base_link` на прямой.
7. На кривой chord yaw и tangent yaw сравниваются, а использованная трактовка явно
   фиксируется в выходе и документации.
8. `z_antenna - 3.0` проверяется на предоставленном примере после нахождения исходного
   `NavSatFix`.
